# S49 — a linear NN at scale, two nets at once, and the cyclic plan that hid both

Date: 2026-08-09 · plan: `components/backend-llvm/plans/plan-s49-linear-nn-two-nets.md`
Raw samples: `benches/results-s49/` (M4 Pro) and `benches/results-s49/i9/` (arch box).
Sources: `benches/nn/*.mapal` (generated by `nn_gen.py`), baseline `benches/nn/nn_numpy.py`.
Harnesses: `benches/nn/nn_ab.sh` (local), `benches/nn/nn_i9.sh` (remote split).

## 0. The finding that had to come first

**Every chained bulk program in this tree was emitting fully sequential code.** A 2-, 3-
or 4-layer net emitted **zero** `mapal_par_*` calls at every size; so did
`benches/shapes/attn_256.mapal`, the project's own chained-matmul corpus shape, which has
been in the tree since S25. A *single* matmul emits 70.

`path_plan` grouped scalar morphisms into **undirected** components of a "shares an object
in any role" graph. Each matmul site builds a capture tuple; all of a program's tuples
capture the same `k` range, so one shared **read** fused every capture group into one task.
Layer 2's group also reads layer 1's output, so that single task was *after* the layer-1
map while every map was *before* it. `nn2x2_128`, pre-fix:

```
task  8: Seq x16  deps=[…, 11, 14]   16 capture Pairs @476 @633 @791 @950
task 11: Split    deps=[0, 8]        layer-1 map @476
task 14: Split    deps=[0, 8]        layer-1 map @791
```

`8 → 11 → 8`. A cycle. Nothing crashes: `llvm/src/lib.rs:261` filters a cyclic plan out
with `path_plan_is_acyclic` and emits the sequential form, so the symptom is *silently lost
parallelism*. `path_plan`'s own `debug_assert_eq!(task_topo.len(), tasks.len())` does catch
it — and is compiled out of every release build. In debug it says `left: 6, right: 11`.

**Fix** (`mapal-ir/src/algo.rs`, one adjacency expression). Component adjacency is dataflow
plus co-writing, never sibling-reading:

| edge | keep | why |
| --- | :---: | --- |
| `in_edges(source)` | ✔ | who produced my input — a chain |
| `out_edges(target)` | ✔ | who reads my output — a chain |
| `in_edges(target)` | ✔ | co-writers of one object are **one** producer (product slots) |
| `out_edges(source)` | ✘ | sibling *readers* of one object have no order between them |

Post-fix `nn2x2_128`'s plan is acyclic and reads as the model predicts — `8→14→9→15` and
`10→18→11→19`, **no edge between the two chains**.

### 0b. And the number the old build printed was fiction

Pre-fix `nn2_2048` self-timed its forward pass at **1.81 ms** — 34.4 GFLOP in 1.81 ms is
19,000 GF/s on a machine whose two SME units cap at ~4,100. The clock fence (`plan-s33b`)
is implemented as **task dependency edges**, which exist only on the parallel path; the
sequential fallback has no fence, and `topo_order` is free to place pure work outside the
bracket — and did, emitting both `mapal_time_ms` calls at lines 68 and 159 with the
`mapal_sme_panel` calls at 269 and 385, *after* both reads.

Whole-process wall time is what settles it (median of 11, generation included in every arm):

| shape | pre-fix (sequential) | post-fix `MAPAL_PAR=1` | post-fix par | pre ÷ post-1t |
| --- | ---: | ---: | ---: | ---: |
| `nn2_2048` | 49.62 ms | 48.77 ms | 20.20 ms | 1.017 |
| `nn4_2048` | 94.23 ms | 92.44 ms | 35.62 ms | 1.019 |
| `nn2x2_2048` | 96.05 ms | 94.52 ms | 35.75 ms | 1.016 |

The pre-fix binary did the same work, single-threaded, and mis-reported it. So **post-fix
`MAPAL_PAR=1` is the honest stand-in for the old behaviour**, and every parallel number
below is the gain. Both new harnesses now hard-error on an emission with no
`mapal_par_task`, because timing the sequential fallback as if it were a scheduling result
is exactly the silent-pass class this tree keeps closing.

### 0c. Cost of the fix, measured

  byte-equality oracle passed — **results are unchanged**.

  reviewed one by one; all four are the same class, one merged scalar task splitting into
  independent ones. `example_fanout` — the example named for fanout — went from **1 task to
  2**. The defect was in the tree's own example corpus.

  two sibling `Div`s and asserted they shared a task. It is about *one task with two trap

## 1. What was measured

Square nets, batch = width = `d`, every layer `d×d`, forward pass only.

| program | shape | independent chains | flops |
| --- | --- | --- | --- |
| `nn2` | X·W₁·W₂ | 1 (depth 2) | 4·d³ |
| `nn4` | X·W₁·W₂·W₃·W₄ | 1 (depth 4) | 8·d³ |
| `nn2x2` | (X₁·W₁ᵃ·W₂ᵃ) ∥ (X₂·W₁ᵇ·W₂ᵇ) | **2** (depth 2 each) | 8·d³ |

`nn4` is the control: identical flops to `nn2x2`, zero available concurrency.

**Value gate: `rel = 0.000e+00` on every cell of both machines** — mapal and numpy agree
bit for bit. Inputs are positive small integers (`(t·a+b) % 9 + 1`) precisely so that
mapal's k-order fold and BLAS's blocked order cannot disagree through cancellation; a gate
that cannot fail is not a gate.

Machines: **Apple M4 Pro** (10P+4E, numpy 2.4.6 → Accelerate, `--target=apple-m4-sme`,
`MAPAL_PAR=14`) and **Intel i9-14900F** (32 threads, numpy 2.3.5 → scipy-openblas,
`--target=raptorlake`, `MAPAL_PAR=32`, `taskset` pinned). Reporting: min for 1-thread legs,
median for parallel legs, 15 interleaved cycles.

## 3. Two nets at once — the auto-parallelism result

Overlap factor **Ω = 2·T(nn2) / T(nn2x2)**. 1 = the two nets ran one after the other,
2 = they fully overlapped. **Ω_ctl = 2·T(nn2)/T(nn4)** is the same flops with no available
concurrency — the control that separates "the DAG overlapped them" from "the machine got
faster at more work".

| d | M4 mapal-par Ω | Ω_ctl | i9 mapal-par Ω | Ω_ctl | numpy-1t Ω | Ω_ctl |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 128 | 1.495 | 0.946 | **2.057** | 1.123 | 1.085 | 1.082 |
| 256 | 1.532 | 1.019 | 1.651 | 1.044 | 1.017 | 1.020 |
| 512 | **1.744** | 1.143 | 1.170 | 0.985 | 1.003 | 1.006 |
| 1024 | 1.125 | 1.005 | 1.060 | 0.949 | 1.002 | 1.007 |
| 2048 | 1.040 | 1.005 | 1.013 | 1.001 | 1.000 | 1.001 |

Stated as the thing a user cares about — **same total work, chained vs two independent
nets, nothing in the source but the dependency structure**:

| machine | d | nn4 (chained) | nn2x2 (2 nets) | gain from the DAG alone |
| --- | ---: | ---: | ---: | ---: |
| M4 Pro | 128 | 0.3636 ms | 0.2301 ms | **1.58×** |
| M4 Pro | 256 | 0.4751 ms | 0.3161 ms | **1.50×** |
| M4 Pro | 512 | 0.8718 ms | 0.5712 ms | **1.53×** |
| M4 Pro | 1024 | 3.1681 ms | 2.8298 ms | 1.12× |
| M4 Pro | 2048 | 20.6452 ms | 19.9572 ms | 1.03× |
| i9 | 128 | 0.3389 ms | 0.1850 ms | **1.83×** |
| i9 | 256 | 0.4771 ms | 0.3017 ms | **1.58×** |
| i9 | 512 | 0.9800 ms | 0.8248 ms | 1.19× |
| i9 | 1024 | 6.6681 ms | 5.9726 ms | 1.12× |
| i9 | 2048 | 45.8525 ms | 45.3210 ms | 1.01× |

On the i9 at d=128 the second net is **free and then some**: two nets take 0.1850 ms
against one net's 0.1902 ms — Ω = 2.06, i.e. running the second net cost nothing measurable
while the first net alone could not fill 32 threads.

**numpy's Ω is 1.00–1.09 at every size on both machines, and its control matches it.** The
sequential source is the baseline on purpose: that is what a person writes. Getting numpy to
overlap two nets requires the user to write the threading; mapal's source says nothing about
concurrency at all.

**The mechanism, and its ceiling.** The advantage is *filling idle width*, not doing less
work. It is largest exactly where one matmul cannot saturate the machine (small `d`, many
cores) and decays to nothing once a single layer already uses every lane — 1.03× at d=2048
on 14 threads, 1.01× at d=2048 on 32. That is a prediction the result confirms rather than a
disappointment: at d=2048 there was no idle width to sell.

### 3b. What refuted nothing, and one thing to distrust

`numpy-mt`'s Ω reads 1.8–4.9 on the i9 at d ≤ 512 — that is **not** overlap. Its control
reads the same, and `nn4` at d=512 (8·d³ flops) runs *faster* threaded than `nn2` (4·d³):
2.64 ms against 6.46 ms. OpenBLAS's threading is unstable at those sizes on this box. Only
the control makes that legible, which is why it is in the table (rule 22).

## 4. Open

1. **The sequential emission has no clock fence.** §0b. It now only reaches
   `is_single_path` programs and any future cyclic plan, and both new harnesses gate on
   `mapal_par_task` — but the fence lives in task edges and the sequential path has none.
2. **`path_plan_is_acyclic` is still needed.** The fix removes the sibling-merge cycle
   class, not every cycle: a scalar value that feeds a bulk op *and* feeds a scalar consumer
   of that op's output would still close one. The `ponytail:` note at `llvm/src/lib.rs:258`
   ("delete this fallback when `path_plan`'s total-DAG contract is enforced") stands.
   `mapal-ir/tests/algos.rs::assert_acyclic` is the pin that exists now.
3. **1 thread is still 0.60–0.87× of numpy** on both machines — S48's standing P0,
   untouched here.
