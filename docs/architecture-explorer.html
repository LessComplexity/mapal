How Mapal turns a short program into fast parallel code

You write what depends on what. Mapal works out what can run at the same time, how to tile it for caches and vector registers, where data must live, and which checks it can safely drop — then emits CPU or GPU code. No threads, locks, tile sizes, or intrinsics appear in your source.

This page follows one program from the top (source text) to the bottom (executable), then opens each layer: syntax, AST, the graph IR, the facts (“plans”) deduced from that graph, and finally how plans plus machine facts become device code. Category-theory words are translated on first use — you do not need them to follow the story.

0How to read this page

Read it in order the first time — each layer only uses ideas from the layer above. After that, use the left navigation as an index. Three reading aids recur:

  • Diagrams show flow. Boxes are artifacts (text, tree, graph, code); arrows are compiler steps. Dotted arrows mean “consults, does not modify.”
  • Expand areas (click the ▸ line) hold full examples, DAGs, and catalog tables. Skim past them on a first read; open them when you need the detail.
  • Plain-words boxes translate the project’s categorical vocabulary. The translation is the whole point: object = a value, morphism = a step that makes a value, functor = a translator that preserves meaning. Nothing deeper is required.

The 60-second version. Mapal source is parsed into a thin tree (AST), then lowered into a single dataflow graph — the Category IR — where every value has exactly one producer. Everything else is deduced from that graph by pure queries called plans (loops, parallelism, tiling geometry, lifetimes, proven-safe indices…). A rewriter simplifies the graph without changing its answer. Backends combine plans with facts about your machine (cache sizes, vector width, GPU shape) and emit LLVM/PTX that LLVM turns into an executable. The interpreter, which runs the graph directly, defines the correct answer; compiled output must match it byte-for-byte.

2Language syntax — Mapal-Core in one sitting

Mapal programs are flows: values move left-to-right through steps joined by ->. There is no hidden control flow — the text you read is the dependency structure the compiler will use. This section covers Mapal-Core, the subset that compiles today (HANDOFF.md §4, docs/spec/user-guide.md). Constructs outside Core still parse and are rejected with a precise P- or L-code diagnostic.

2.1 The smallest useful program

fn main() {
    1048576 -> iota -> ts;
    ts -> map { t -> t * 2 } -> doubled;
    doubled[1048575] -> println;
}

Read each line as a pipeline: make the range 0..1048576, double every element (in parallel — nothing says so, the graph proves it), print the last one. Bindings (-> ts;) name an intermediate so later flows can use it. A flow is a statement, not an expression: it routes a value; it does not itself produce one.

2.3 Bindings, mutation, element update

5 -> x: i32;              // immutable binding (flow form)
mut counter: i32 <- 0;    // mutable binding (assignment form)
counter + 1 -> counter;   // legal only because counter is mut
c[t] <- v;                // element update: "c with slot t replaced" (a fresh value in the IR)

Immutability by default is load-bearing: an immutable value can be read by any number of parallel branches safely. c[t] <- v looks like mutation but denotes a new array value in the graph (Update, §5) — whether it is stored in place is a backend decision guided by last_use_plan (§6).

2.4 Functions

fn clamp(v: f32, lo: f32, hi: f32) -> f32 {
    (v > hi) -> {
        -true->  hi;
        -false-> v;
    } -> ret;
}

fn main() {
    (270.2, 0.0, 255.0) -> clamp -> r;   // tuple input, one step
    r -> println;                          // 255
}
  • ret names the function’s output; ret.0 / ret.1 fill tuple slots. At most one full-value writer may reach ret (checked as T0101).
  • A function conceptually takes one input — a tuple when it has several parameters. This single-input rule is what keeps the graph uniform (§5).
  • Recursion is out of Core by design (L1008): cycles live in loop dataflow, never in the call graph. Iteration is written with loop (§2.7) or fold (§2.6).
  • main takes no parameters and declares no return.

2.5 Pipelines and shorthand stages

fn f(data: i32) -> i32 {
    data * 2
        -> + 5        // shorthand: piped value is the left operand
        -> ret;
}
// f(10) = 25

A shorthand stage like -> + 5 means “pair the piped value with 5, then add.” In the AST it is an OpShorthand stage whose expression contains a single Hole leaf for the piped value; in the IR it becomes an ordinary Pair + Add (§4, §5). Naming intermediates (-> s1;) changes nothing semantically — it only labels a graph node.

2.6 Collections: map, fold, and the pure builtins

(a, b) -> zip -> map { p -> p.0 + p.1 } -> c: [i32; 16];   // elementwise add
(0, c) -> fold { acc, x -> acc + x } -> total;              // sum, in order
16 -> iota -> ts;                                            // [0,1,…,15]
arr -> enumerate -> indexed;                                 // [(0,a0),(1,a1),…]
7 -> fill -> sevens: [i32; 4];                               // [7,7,7,7] (count from the type)
t -> widen_f64 -> wide;                                      // i32 → f64 (also widen_i64, widen_f32)
  • map { x -> … } applies an inline block to every element: [T; n] → [U; n]. The block may capture enclosing values (arrays included) — captures are broadcast to every element and recorded explicitly in the IR.
  • fold { acc, x -> … } threads an accumulator in index order: (Acc × [T; n]) → Acc. Order is part of the meaning unless the compiler proves a regrouping is allowed (§6, fold_tree_step).
  • The block is not a first-class function value; lowering turns it into a real (anonymous) function in the graph (MapBody / FoldBody).

2.7 Choice and repetition: guards and loop

// Choice — a guard block. Arms are pure; only the taken arm computes.
op -> {
    -0-> a + b;
    -1-> a - b;
    -2-> a * b;
    -3-> a / b;      // does NOT run (and cannot trap) when op is 0
    -_-> a % b;      // default
} -> ret;

// Repetition — a loop is a cycle in the dataflow, steered by a guard.
mut k: i32   <- 0;
mut acc: f32 <- 0.0;
loop {
    (k < 4) -> {
        -true-> {
            acc + coeffs[k] * signal[4 + k] -> acc;
            k + 1 -> k;
            -> loop;          // back-edge: go around again
        }
        -false-> acc -> ret;  // exit edge
    }
}

Guard discriminants in Core: -true->, -false->, integer literals (-3->), and the default -_->. Pure guard blocks lower to a Phi (choose-one) step in the IR; which arm’s work is gated (skipped when not taken) is decided by guard_plan (§6). Both arms are always compiled; computing is what is conditional.

2.8 Fanout (parallel by default) and seq

6 -> {
    -> square -> sq;     // branch 1 — independent
    -> double -> db;     // branch 2 — independent, may run at the same time
}
// implicit join: both sq and db are available here
sq -> println;
db -> println;

Fanout branches are headless flows starting from the piped value. Independence is structural: if no branch needs another’s result, they are parallel — no keyword required. Effects (print) may not appear inside a fanout branch (T0201); they belong to the sequential “host spine.” A seq { … } stage is the opposite: an explicitly ordered statement block. It leaves no footprint in the IR — ordering there comes from data dependencies and the effect token (§5).

2.9 Effects, time, and precision annotations

"total = " -> print;      // raw, no newline
total -> println;         // with newline
() -> time -> t0;         // monotonic clock read (milliseconds, f64) — effectful, never reordered

(a, b) -> fold: tf32 | f32 { acc, k -> acc + a[k] * b[k] } -> s;
                          // ": compute" — products in this body admit TF32 operands (ADR-0041)
  • print/println and time are the only effects in Core. In the graph they thread a linear IO token, which is what pins their order (§5).
  • A : compute annotation (: tf32 | f32) on a function, loop/seq block, or map/fold step widens the set of precisions its float products admit. Default is full f32 with an a-priori error bound (§6, precision_plan; §8).
  • Operators: + - * / %, comparisons == != < > <= >=, logic && || !, unary -. Division/modulo by zero and out-of-bounds indexing are traps (defined failures), reported in source order.

3AST — what it is and how it is created

The AST is a thin parse tree: syntax, names, spans, literal values, and flags — nothing more. It does no name resolution, no type inference, and no effect classification (crates/mapal-syntax/src/ast.rs). Think of it as the deserializer’s scratch space: faithful to the text, including its mistakes, so diagnostics can be precise. The program, for all later purposes, is the graph (§5).

3.1 Step by step

  1. Lex. lex(&str) produces tokens, each a kind plus a byte-range SourceLoc { start, end } into the original text. Token text is never copied — consumers slice &source[span] (single source of truth). Malformed literals yield L-code diagnostics but lexing continues.
  2. Parse. A hand-written recursive-descent parser builds the tree following the §2 grammar. Every node carries its span. On error it recovers (synchronizes to a plausible boundary) and records an Error node, so one run can report many problems — 32 P-codes in total.
  3. Keep the rejected. Forms outside Core (function-call syntax f(x), ?, dynamic arrays [T], custom loop labels, pattern guards) are kept as dedicated node kinds with their diagnostic, rather than silently mis-parsed. Lowering’s job is then a clean “defined exactly on Core” partial map (§4).
  4. Merge + sort. Lex and parse diagnostics are merged and stably sorted by (span.start, span.end). The public entry is parse(&str) -> ParseOutput (crates/mapal-syntax/src/lib.rs).

Three things to notice. (1) The shorthand -> + 5 is already an expression tree with a Hole placeholder — the parser classifies it; lowering just substitutes the incoming value. Expand: why keep a tree at all? (vs parsing straight to the graph)

Because the tree is the only place that can represent a broken program, declaration order freedom (lowering walks items three times: types, signatures, bodies), and fanout scope for the effect check. The measured price is ~4 µs of parsing against ~140 ms of LLVM on a real compile. Skipping the tree would save microseconds and cost all three properties. Full argument: docs/architecture/INDEX.md.

4Lowering & checks: tree → graph

lower(&str, &Program) -> Result<CategoryIr, Vec<Diagnostic>> (crates/mapal-lower/src/lib.rs) turns a parse-clean tree into the sealed graph. It is the one place where names become edges. Precondition: the tree came from a diagnostic-free parse; anything else yields L1000, never a panic.

4.1 What lowering does, in words

  1. Types first (A). Surface TyKind values are resolved to IR Ty values: named types are looked up and structs inlined, depth is bounded (MAX_TY_DEPTH = 64), and anything outside the Core whitelist is refused. The two Ty types are genuinely different types joined by this partial translation — do not conflate them.
  2. Effects + call graph (B). Which functions can (transitively) print or read the clock, and is the call graph acyclic? A recursive cycle aborts here with the teaching diagnostic L1008.
  3. Typing walk (D1). Each function body is type-checked; this pass collects many errors. Emission afterwards is fail-fast and assumes a well-typed-enough tree.
  4. Declare + emit (C, D2/D3). Each function gets exactly one input object and one output object. Scopes map names to objects; every computation step becomes one morphism built through the checked IrBuilder. Inline map/fold blocks become anonymous functions; captured variables become leading tuple components.
  5. Seal (E). The builder freezes the graph. From here on it is immutable; the only way to “change” it is to build a new one (which is exactly what the rewriter does, §7).

4.3 The two gates after lowering

  • validate (crates/mapal-ir/src/validate.rs) is an independent oracle: it re-derives every graph invariant from scratch without sharing builder code. The property “seal succeeded ⇒ validate finds nothing” is property-tested. It runs in tests/debug, not as a mandatory production pass.
  • check (crates/mapal-check/src/lib.rs) discharges exactly what the interpreter assumes: T0101 — at most one full-value writer per return object; T0201 — no effectful step inside a parallel fanout branch. It needs the tree as well as the graph, because fanout scope is precisely what lowering erased. This is the one place the tree is consulted after lowering; everything downstream sees only the graph.

5Category IR — the graph, in plain words

Forget the word “category” for a moment. The Category IR (CategoryIr, crates/mapal-ir/src/graph.rs) is a dataflow graph: circles are values, arrows are steps that compute a value. The categorical names stuck because the design borrows two ideas from that world — compose steps by matching output-to-input types and translate the whole graph with meaning preserved — but the data structure itself is ordinary Rust: three slotmap arenas with deterministic iteration order and no HashMap anywhere.

Vocabulary translation (the only category theory on this page).
Object → a value (with a type).   Morphism → a step: one directed edge source → target labeled with an operation.   Composition (f -> g) → plumbing: feed f’s output into g.   Product (A × B) → a tuple.   Functor → a translator (a backend) that maps the graph to another world while preserving the plumbing, hence the answer.   Trace → feedback: a loop.

5.3 The rules the graph guarantees

These invariants (DESIGN “I-codes”) are what every plan silently relies on. In plain words:

  • One producer. Every non-constant, non-parameter value is written by exactly one edge (a LoopMerge excepted: one enter + back-edges). Dataflow dependencies are therefore exact — no alias analysis, no “may-def” guessing.
  • Typed plumbing. Every edge type-checks locally against its operation’s signature.
  • Tokens stay linear. The IO token is never duplicated or dropped, so effect order is structural.
  • Determinism. Arena storage iterates in insertion order; dumps, topo orders, and emissions are byte-stable across runs.
  • Sealed = trustworthy. Graphs can only be built through the checked builder and are immutable afterwards. Consumers never defensive-check structure the builder already proved.

6Plans — the facts deduced from the graph

A note on the title first, because it corrects a common first guess: plans are not built on the AST. The tree is discarded after lowering/checking. Every plan is a pure query over the sealed graph: fn plan(&self, f: FuncId) -> Plan on CategoryIr in crates/mapal-ir/src/algo.rs (≈ 6,300 lines — the intellectual center of the compiler). “Code → plan” therefore means: source → graph → the fact the graph proves. This section is the central record of those plans, their algorithms, and who consumes them.

6.1 The four rules every plan obeys

  1. Facts live on the graph. Each fact is computed at most once per (graph, function) and stored in a pre-allocated OnceLock slot (crates/mapal-ir/src/facts.rs). Facts depend on other facts (path_plan reads loop_plan; tile_plan reads bounds_proof), forming a small dataflow of their own. A query reads the stored value; nothing recomputes per call site.
  2. Partial = safe. If a plan cannot prove its shape, it returns None / empty / false and the compiler takes the slow correct path. A plan can cost performance when silent; it can never change the answer.
  3. Machine-free. mapal-ir answers “is this legal?” (geometry, independence, proofs). Backends answer “is this worth it?” using TargetProfile (§8). No cache size or GPU fact ever enters a plan.
  4. One question each. New logic starts by checking this catalog. If a needed fact is missing, it is added here as one tested query — never re-derived inside a backend pass (AGENTS.md standing rule).

6.2 The catalog

Filter by text or by group. Each card states the question in plain words, the algorithm sketch, the consumer, and the fallback when the proof fails. Groups: structure order & loops · parallel tasks & gating · geometry kernel shapes · memory lifetimes & materialization · safety proofs & precision.

topo_order(f) -> Vec<MorphismId>structure

Question: in what single order could this function execute, respecting every dependency?

Algorithm
Kahn-style ready walk with a min-heap keyed by (loc.start, loc.end, insertion index) — source order, not compiler-construction order. That choice is observable: when two independent steps can both trap, the one earlier in your source is reported (§9).
Consumers
Everyone: interpreter walk, sequential emission, and as the position basis for last_use_plan.
Fallback
None — total on well-formed graphs (cycles only inside loop SCCs, handled by loop_plan).

sccs(f) · loop_structure(f) -> Vec<LoopScc> · loop_plan(f, merge) -> Option<LoopPlan>structure

Question: where are the loops, and for each one: what is the initial state, the merge point, the decide/advance order, and the exits?

Algorithm
Tarjan SCC over objects; an SCC containing a LoopMerge is a loop region. loop_plan then checks the canonical shape (one LoopEnter, shared condition Bool, exits leaving the region) and records init/merge/decide/advance/exits.
Consumers
Interpreter loop driver, rewrite replayer + loop lifting, both backends’ loop CFGs, path_plan, trip_split, last_use_plan (two-iteration liveness).
Fallback
None ⇒ the region is treated as opaque sequential work; never miscompiled.

path_plan(f) -> PathPlan (+ is_single_path)parallel

Question: what can run at the same time, as an explicit task DAG — and where must the sequential (effectful) world wait?

Algorithm
(1) Order by topo_order. (2) Set aside the host spine: token-touching steps and effectful loops become ordered checkpoints. (3) Bulk ops (Map/Zip/Enumerate/Iota/Fill) → Split tasks (element range sliceable); Fold → Seq task; each loop region → one Seq task; remaining scalars grouped by dataflow+co-writing connectivity (never mere sibling reads). (4) Dependencies = “the task that produced each input object” — direct dataflow is the complete relation. (5) Rank = critical-path weight, long poles first. (6) Checkpoints carry per-task watermarks (past-last-trap) or completion when the value is consumed.
Consumers
LLVM backend → one @taskN per task + static dep/rank table → mapal-rt work-stealing pool (§8, §9).
Fallback
Single-path (or malformed) plan ⇒ plain sequential emission.

guard_plan(f) -> Vec<GuardSite> (+ gated())parallel

Question: for each Phi (guard), which work belongs exclusively to each arm — and must that work be gated (not computed when the arm is not taken)?

Algorithm
Per-arm consumer closure (work whose every consumer is inside the arm), with loops joining as whole units via loop_plan. Transitive can_trap/heavy flags through nested sites. Legality first (can-trap must gate), then cost (heavy work gates; two scalar arms are left branchless).
Consumers
Interpreter (skip unchosen arm), LLVM + CUDA host emission (branch around gated work). Both arms stay in the binary.
Fallback
Not gated ⇒ both arms compute, Phi selects — correct only where both arms are total, hence the must-gate rule.

tile_plan(f) · tile_plan_strided(f) · tile_plan_radix(f) → TileSite / TileReadgeometry

Question: is this innocent “one result per element” map secretly a tiled kernel — neighboring outputs computed by lockstep folds reading broadcasts and vector runs?

Algorithm
(1) Skeleton: Map over iota whose body ends in exactly one Fold. (2) Coordinates from a t/C, t%C split (2-D) or the element itself (1-D). (3) Chain shape acc + x*y (either operand order). (4) Each read address decomposed affinely as base + ci·i + clane·lane + ck·k: clane=0 ⇒ broadcast, clane=1 ⇒ vector load, anything else ⇒ refuse. Strided/radix variants widen the coordinate reading (see radix_plan). TileKSplit records when the k axis itself may be split.
Consumers
CPU tiled micro-kernels (NEON/AVX/SME), GPU tile kernels (§8). Records geometry only — tile sizes come from TargetProfile.
Fallback
No site ⇒ ordinary elementwise map emission. Matmul, FIR, conv and attention shapes all match; there is no “matrix” concept in the recognizer.

cell_plan(f) → CellSite / CellRead (+ tree)geometry

Question: per output cell of a map, exactly what does it read — and is its fold step regroupable as lane partials + a tree?

Algorithm
Generalizes the tile reading per cell: affine reads with reach classification, independent cells across threads. CellSite::tree marks steps whose order is free (§6 fold_tree_step), enabling tree reductions where the float face permits (§8).
Consumers
GPU one-thread-per-cell / cooperative kernels; CPU cell kernels.
Fallback
No site ⇒ generic map path.

footprint_plan(f) -> FootprintPlan (of, rect, at)geometry

Question: for each consumer, what region of each producer does it actually touch?

Algorithm
Per producer→consumer edge, the touched footprint (rectangles / affine reaches with taps). This is the fact that replaces any “fusion pass”: whether work runs together, stays in registers/shared memory, or is stored follows from footprints + death points + the target (§8). Kernel boundaries are a result, never a pass.
Consumers
Backend work-unit formation, residency and staging decisions.
Fallback
Whole-array footprint ⇒ materialize and pass the buffer.

elem_plan(f) -> ElemPlan · map_law(m) -> Option<ElemSrc> (+ Outside)geometry

Question: what is out[i], as a closed function of i — can a consumer recompute (or directly source) elements instead of materializing the array?

Algorithm
Per array object, an ElemSrc law: element i expressed via sources, piecewise when every cell outside a row/range/column/single cell is a capture’s own element (the in-place range-map shape). map_law gives the same for one Map.
Consumers
Backends decide recompute-vs-store per target (GPU: usually recompute; CPU: vs L2 round-trip; FPGA: BRAM vs area) — the plan records legality, never the choice.
Fallback
No law ⇒ the array materializes.

row_fold(f) · whole_fold(f) → RowFoldSite / RowFoldOp · fold_tree_step(fold)geometry

Question: is this fold really “one row at a time” (or the whole function folded over one affine read) — and may its step be regrouped?

Algorithm
Recognize folds whose reads are affine in (row, k): softmax/decode and reduction shapes. fold_tree_step proves the step is an order-free combine (e.g. +/max under the admitted face), licensing lane-partials + tree reduction.
Consumers
Row kernels, split-K / tree-reduction emission.
Fallback
Sequential accumulator chain, exact source order.

move_plan(f) -> MovePlan / MoveSitegeometry

Question: where is data merely moved (transposed, gathered, re-laid-out) rather than computed — with what affine source pattern?

Algorithm
Sites whose element law is a pure affine re-indexing of one source. Backends traverse them in cache-blocked panels derived from TargetProfile geometry instead of element order.
Consumers
Transpose/pack/panel traversals on CPU; staging on GPU.
Fallback
Element-order copy.

emission_plan(f) -> EmissionPlan (class(o))memory

Question: which objects must actually materialize in emitted code — and which are just graph plumbing?

Algorithm
Classify each object: dissolved (products/views — no bytes, e.g. Pair tuples), inline (single-use scalar, emitted at its use), or named (needs storage), from consumer counts and kinds. Minimal emission: if it has no bytes in the semantics, it gets no bytes in the binary.
Consumers
All backends (naming, SSA/alloca decisions); CUDA minimal-emission path.
Fallback
Named ⇒ allocate; always safe.

last_use_plan(f) -> LastUsePlan (position · death · escapes · carried_by · dead_after, view variants)memory

Question: for each value, where is its last read — does it escape into the output, is it carried around a loop, and after which step is its storage free?

Algorithm
Positions from topo_order; death = max position over consumers; carried_by marks values crossing a LoopBack (live across two iterations); view-aware variants track dissolved products to their storage. Lifetimes are exact because every read is an edge.
Consumers
Buffer coloring/reuse (arena), in-place Update, free-at-back-edge, host↔device retention (§8). This is Mapal’s “memory model”: no GC, no ownership annotations — last-use is the lifetime.
Fallback
Escaping/unknown ⇒ keep alive to function end.

write_delta(f) → per-object Deltamemory

Question: for a loop-carried array, what contiguous range does each trip actually write?

Algorithm
Chase Updates and piecewise map laws around the loop to a per-trip written interval. A partial update then moves/retains only the delta across host↔device or iterations, instead of the whole array.
Consumers
Residency/retention, delta copies, cache decisions.
Fallback
Whole array is the delta.

trip_split(f) -> Vec<TripSplit> (TripPhase)structure

Question: for a counted loop, what trip intervals do guards on the counter cut out — which state is recurrent in each, what work sits outside, and can all-but-last trips of the first interval be skipped?

Algorithm
Counter-guard analysis over the loop_plan: phases with their recurrent slots, batched row writes, and the skip fact. Turns “loop with cases inside” into “phases the backend can schedule separately.”
Consumers
Loop emission (phase splitting, batching).
Fallback
One phase = the whole loop, guard evaluated per trip.

bounds_proof(f) -> BoundsProof (proven(m))safety

Question: which Index/Update steps are provably in bounds, so their trap guard can be dropped?

Algorithm
Affine/range reasoning over index expressions against static array sizes (iota-derived indices, div/mod decompositions, counter ranges). Only proven guards drop — “which bounds checks are provably unnecessary, and only those.”
Consumers
Guard elision in LLVM + CUDA emission; also read by tile_plan/path_plan (trap capability feeds watermarks).
Fallback
Unproven ⇒ keep the check; the trap remains possible and ordered.

precision_plan → set · round_at · cross · bound (ADR-0041/0040)safety

Question: which precisions does each float product admit, where may a value be rounded (once, at its producer), which edges must a rounded copy not cross, and what is each tile site’s a-priori error bound?

Algorithm
From the per-Mul admitted sets (innermost : compute wins): propagate rounding points to producers, mark edges a rounded copy would corrupt, and compose the weakest-member bound per site. Default face: full precision + bound + unspecified order, fastest on the native CPU+GPU; exact/contract faces are opt-in (§8).
Consumers
TF32/tensor-core eligibility, value gates in tests (check the bound, not bit-equality, on the default face).
Fallback
{f32} everywhere — no rounding, bound is the f32 one.

radix_plan(f) → RadixFormgeometry

Question: is this integer really “digits” of the inputs — (x ÷ s) % r with constant divisors?

Algorithm
Recognize constant div/mod digit decompositions per object. Map/fold reads affine per digit then become tile sites over (i, lane, k) — the implicit-GEMM reading that lets convolution-shaped index arithmetic reuse the tile machinery.
Consumers
tile_plan_radix → tile kernels for conv/window shapes.
Fallback
Plain integer arithmetic, ordinary addressing.

Supporting queries you will meet in the source: func_objects (a function’s object set) and per-function trap capability (can this function trap, transitively?) — both stored facts feeding the plans above. Deep dives with line references: docs/architecture/deduced-queries.md.

8.1 TargetProfile — machine facts as data

crates/backends/llvm/src/profile.rs: one record per part (e.g. Apple M4 + SME variant, Raptor Lake, cuda-ada sm_89, H100 sm_90a, RTX 5090 sm_120, RTX 3090 sm_86, plus generic and auto-detected native). It holds only hardware facts — L1d geometry (sets/ways/line), L2 size, vector width, matrix-unit shape, measured dispatch economics, and for GPUs: SM count, schedulers, warp size, shared-memory budget, MMA/WGMMA capability, copy costs. Derived helpers (tile_i, move_block, gpu_tile, pack_pays, device_pays, raster…) turn facts + a site’s extents into concrete constants. A profile with no measured number carries None and the corresponding optimization simply does not fire — no part is made worse by a number nobody took.

Geometry ports; constants don’t. Which reads broadcast, which axes split, what may interleave — deduced once, backend-independent (tile_plan, path_plan). Tile factors, panel depths, unroll counts, task grain — facts about a cache hierarchy and a register file, measured per target and kept in the profile. That split is the project’s answer to “portable performance”: the algorithm ports, the tuning is a per-machine table.

8.2 The CPU path (LLVM backend)

Entry: emit_detailed(ir, &EmitOpts) -> Emission { text, device, profile_name } (crates/backends/llvm/src/lib.rs). Emission is a pure function of (graph, options, profile) — same triple, same text. Per function, the emitter (src/func/: core · frame · drive · ops · tile · window · conv · packed · trio · vec · bulk) walks the plans:

  1. Frame + storage (frame, reuse.rs): emission_plan decides what gets an alloca slot vs dissolving to SSA; last_use_plan colors buffers so dead storage is reused; frame aliases let an Update whose source dies here write in place.
  2. Scheduling (drive): if path_plan is not single-path, emit one @taskN per task + the static dependency/rank/checkpoint tables for mapal-rt (§9). Before dispatching, a roofline test asks whether the task can pay for its own dispatch (max(flops/rate, bytes/rate) vs measured dispatch_ns); one-slice tasks run on the calling thread. Otherwise emit plain sequential code in topo_order.
  3. Kernels (tile · packed · window · conv · vec · bulk): a TileSite becomes a register-blocked micro-kernel nest — pack the strided operand into panels (only when pack_pays: working set > L2), block for L1/L2 from profile geometry, keep accumulators resident across k, store once. The innermost leaf differs per part (scalar FMA / NEON / AVX / ARM SME fmopa into ZA tiles); the nest around it is shared. MoveSites traverse in conflict-avoiding panels; window/conv sites reuse the same geometry with tap reads.
  4. Loops + guards (loops.rs, trio): loop_plan → a CFG with phis for carried state; guard_plan.gated() → branches around gated arm work; bounds_proof → omitted trap branches. Traps that remain call the runtime trap path with the source-order index (§9).
  5. Hand off to LLVM. The emitted IR is deliberately shaped for LLVM to derive the schedule: accumulators as SSA so SROA keeps them in registers, affine accesses so the vectorizer and LSR fire, contract flags only on the contract float face. clang -O3 does the rest (≈ 99% of compile time).

8.3 The GPU path (NVPTX device module + host orchestration)

The GPU leg reuses the same LLVM backend: device-suitable sites are emitted as an NVPTX module (PTX text embedded beside the host IR), and the host code launches them. This is the one place physical location is real — host vs device are different places, and every host↔device copy is a typed, costed transmission the facts must justify.

  1. Placement. For each candidate site (tile/cell/row-fold/bulk), device_pays compares estimated device time + required copies against staying on the host, using footprints, extents vs SM count, and whether operands are already resident. Unplaced work runs as CPU tasks — a program is CPU-only, GPU-only, or mixed, per site.
  2. Residency + arena. last_use_plan + write_delta + footprints deduce, per object (loop-carried state included), where it lives, what is reused, and what is retained across launches. Buffers are lifetime-colored in a device arena; any copy or allocation the dataflow facts do not require is treated as a bug (a “finding”), never a default. Partial loop updates move only their delta.
  3. Kernel formation (the flow rung). There is no fusion pass. Work units follow producer/consumer footprints, death points, and cell independence: a value with several readers is computed once; independent cells spread across threads; folds with a proven tree step become lane partials + tree/warp reductions. Kernel boundaries fall out of where values must materialize.
  4. Kernel leaves. Per site geometry + GpuTile derivation: thread/block tile shape, shared-memory staging (optionally cp.async/LDGSTS double-buffering), register accumulators per thread, mma.sync/wgmma tensor-core leaves where the face + precision_plan admit them (TF32 operands rounded once, accumulation in f32), split-K where TileKSplit allows, rasterization order for L2 reuse.
  5. Rungs. Each GPU kernel optimization is a named boolean rung in GpuRungs (e.g. async staging, warp specialization, wide FMA, min-blocks). Defaults are per-arch and evidence-gated: GPU_RUNGS_OFF rows record, with citations, where a rung measured negative on a (part, grid-fill, face) class. A mixed win/loss is treated as a missing fact to be added — an OFF row is a stopgap, tracked as open work. Every rung has an OFF measurement arm (--gpu-off=/--gpu-on=).
  6. Lowering. LLVM NVPTX emits PTX; ptxas/driver produces SASS. What LLVM must derive (vector widths, unroll, FFMA contraction…) is declared up front per rung and then checked in the realized PTX/SASS — see the evidence pass below.

The older standalone CUDA-text backend (crates/backends/cuda/: host emitter + kernel emitter + arena) remains as the host-form reference; new device work lands in the NVPTX leg. The Verilog backend (crates/backends/verilog/) is the planned third translator — the same graph to clocked hardware with a done-protocol — evidence that the dataflow model reaches past SIMT machines.

Expand: the evidence pass — how optimization decisions are kept honest

No keep/remove/gate decision stands on timing alone (AGENTS.md). For every optimization or codegen change:

  1. Intent, before measuring. Declare machine-checkably what LLVM/NVPTX must derive from the emitted IR, which PTX/SASS features must appear/disappear (instruction mix, vector widths, FFMA-per-load, registers, spills, occupancy, launches), and what data movement the facts require per program and per loop trip.
  2. Realized. Collect LLVM optimization remarks, PTX, SASS (cuobjdump/nvdisasm), and ptxas -v for every measured kernel/arch; check against intent. A mismatch is a finding, never a pass. Library kernels (cuBLAS/CUTLASS) are captured from the actual launch.
  3. Explain. Every decision-driving timing difference cites the SASS/usage difference that explains it. Unexplained ⇒ the decision stays “open.”
  4. Breadth + genericity. Judge on the multi-workload suite (GEMM/MLP, attention/softmax, reductions, FIR/conv/window, elementwise chains, fan-in/out, loops; CPU-only, GPU-only, mixed) against the best library or PyTorch — and validate every rule on unseen generated programs (values vs oracle/bound, plus movement/kernel intents). Benchmarks are acceptance only; programs are written idiomatically and never reshaped to flatter the recognizer. Tooling: benches/gpu/intent.py, evidence.py, rejudge.py — a GPU run without its evidence.tsv is not a result.

9Runtime & execution semantics

9.1 The thread pool (mapal-rt)

Compiled parallel programs link mapal-rt (crates/mapal-rt/src/lib.rs), a work-stealing pool executing the static task table the backend emitted from path_plan. Tasks unlock as their producer dependencies retire; Split tasks slice their element range across lanes; ranks schedule long poles first. MAPAL_PAR sets total executors including the host thread (MAPAL_PAR=1 is the sequential lever). Hard-won details, all measured: dispatch wakes only the lanes it filled; the completion path is lock-free; the host spins briefly before parking while workers do not (spinning workers measured worse and were removed).

9.2 Checkpoints, watermarks, and trap order

  • Effectful steps (prints, clock reads) run on the host in program order. Before each, the runtime waits only as much as the checkpoint demands: completion if the effect consumes the task’s value, else its watermark — past its last trap-capable point — so “the task trapped” is always observed before “the print ran.”
  • When several independent steps could trap, the reported trap is the earliest in source order: the interpreter walk, sequential emission, and the parallel runtime’s minimum-index reporting all derive from the same topo_order key, so they cannot disagree. Output written before the trap is preserved.
  • The interpreter (mapal-interp: fueled graph evaluator + SCC loop driver) is the oracle for all of this. Differential tests require compiled stdout/traps to match it byte-for-byte at -O0 and -O2, at any MAPAL_PAR — and, for placed programs, under any CPU/GPU placement on the exact/contract faces.

Determinism is a feature, not an accident. Arena-ordered storage, source-ordered topo, rank-ordered tasks, and order-pinned folds mean the same source produces the same bytes on every run and every thread count. Where the default float face frees the order, it does so explicitly, with a bound (§8.2).
