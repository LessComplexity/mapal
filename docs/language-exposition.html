A language exposition

Describe how data flows. Mapal places it where it runs best.

A Mapal program states each value and what it is made from — never threads, kernels or where data lives. The compiler matches that flow to the machine in front of it and places every step where it runs best: on CPUs and NVIDIA GPUs today, and on any hardware by design.

A piece of Llama-3.2-1B

RMSNorm, as it is in the model: the whole of examples/llama.mapal is 403 lines, weights read from a file.

// RMSNorm of each vector: x / sqrt(mean(x^2) + epsilon), times a learned gain per feature.
fn rms_norm<tokens>(x: [f32; tokens * hidden_size], gain: [bf16; hidden_size]) -> [f32; tokens * hidden_size] {
    hidden_size -> iota -> features;
    hidden_size -> widen_f32 -> width;
    tokens -> iota -> map {
        t -> (0.0, features) -> fold {
            sum, i -> sum + x[t * hidden_size + i] * x[t * hidden_size + i]
        }
    } -> sum_of_squares;
    tokens * hidden_size -> iota -> map {
        cell ->
        sum_of_squares[cell / hidden_size] / width + rms_epsilon -> sqrt -> root;
        gain[cell % hidden_size] -> widen_f32 -> g;
        x[cell] * (1.0 / root) * g
    } -> ret;
}

2Performance

Where Mapal is faster and where it is slower, by kind of problem, each against the best library or compiler at the same precision. Blue is Mapal faster, red slower. Every chart is drawn from the repository's measurement files when the page is built.

On GPUs: six kinds of problem

Five NVIDIA GPUs, 119 programs timed on every one. Against cuBLAS, cuBLASLt, CUTLASS, PyTorch eager and torch.compile, FlashAttention, Triton and hand-written CUDA.

Attention and softmax

Leads: a chain of steps runs together and saves the launches between them. Trails a memory-efficient attention kernel on long f32 prefill, which skips masked blocks.

Convolution and FIR

Leads on every GPU. The one loss is the TF32 multi-channel convolution, against a tensor-core library.

Fan-in / fan-out chains

About even. Merging launches only pays where the phases are short.

Matrix products

The weak class. Matrix-vector shapes are limited by how many bytes the kernel keeps in flight, and the H100’s TF32 products trail cuBLAS by 1.3–3×; why is still open (cuBLAS’s own kernels were not captured).

LLM layers

Ahead in f32. Behind in bf16 where torch.compile with CUDA graphs replays many small kernels without launch gaps.

MLP chains

About even with the best chain of library calls: the time is in the matrix products.

The same suite, all programs: faster than the best on average on three of the five GPUs.

On CPUs: against NumPy

An earlier measurement on an Apple M4 Pro, kept in docs/performance/earlier-readme-results.md with the i9-14900F tables and the OpenBLAS comparison. Mapal wins the streaming shapes by a wide margin and trails on a plain sum and on small matrices; against OpenBLAS on the i9 it ties at best.

One whole model: Llama-3.2-1B

The readable source above against the fastest of gpt-fast, vLLM, SGLang, TensorRT-LLM, llama.cpp and Hugging Face on five GPUs, each at the same precision. A bar below 1.0 means Mapal is faster.

After the 16-bit warpgroup tiles (wgmma), on another H100 against gpt-fast on the same box, the bf16 time to first token at 128 / 512 / 2048 tokens is 0.75 / 1.25 / 1.58 of gpt-fast's (2.7 / 5.6 / 18.11 ms against 3.58 / 4.47 / 11.45 ms): ahead for short prompts, behind for long ones. Source: full-model.json, H100 reruns.

Full precision (f32)

The fastest on all five GPUs at generating text, and for prompts of 512 tokens or more.

Half precision (bf16)

Mostly still behind the fastest engine: within 5–15% on the RTX 5080, further behind on the others. On the H100 it is faster for short prompts. Work is in progress.

Memory

2.7–3.5 GB of GPU memory, level with the leanest engines and far below the serving engines.

3Philosophy

Six ideas. Each one is something you have already seen above.

The language is the flow

A program states data and how it flows, data -> transform -> result;, not the control that moves it. A map says cells are independent; a fold says how they combine.

See three steps over every sample.

Facts, not passes

What each value reads, when it dies, what is independent: every analysis is a stored fact on the graph, and every optimization decision reads facts.

See attention, the loop.

Hardware is physical properties

Compilation matches the shape of the work to compute units and storages: sizes, bandwidths, latencies. Never a branch on a chip's name.

See one source, three machines.

Correct within a stated error

A result is guaranteed within a bound you can see, not bit for bit. That frees the compiler to choose the fastest correct order, tensor cores included.

See the norm and fold: bf16 | f32 in the projection.

Readable code is the target

If the natural version of a program runs slower, the compiler is fixed; the program is never rewritten to suit it.

See softmax, RMSNorm.

Made for AI agents too

One way to write each thing, exact error messages, a formatter, a language server, and a reference interpreter to check every result against.

Every output above is the interpreter's (mapal run --interp).

The full philosophy text, with the decisions behind it, is in In depth.

4The architecture as an equation

Code becomes a dataflow graph plus the facts deduced from it. Hardware becomes compute units plus storages. Put together, and compiled, they give something runnable.

Where this stands. The hardware model is ADR-0050: the machine as memory places and compute units with operations as geometry, and one cost model plus a search that places the dataflow on it. It is being built; step 1 (matrix products) is in progress and the search is off by default (machine-place). Today the placement is decided by about seventeen separate rules, each reading the hardware properties it needs, and every rule is replayed against the measurements that justified it. The compiler you see in the demos is that one.

Not new on its own: dataflow languages (SISAL, Id — the 1980s and 1990s), size types (Futhark), separating the algorithm from its schedule (Halide), analytic mapping onto accelerators (Timeloop), floating-point error analysis (FPTaylor).

The 60-second version. Mapal source is parsed into a thin tree (AST), then lowered into a single dataflow graph — the Category IR — where every value has exactly one producer. Values whose dataflow reads no input are computed before the program runs. Everything else the compiler knows about the program is deduced from the graph by pure queries called plans (loops, parallelism, tiling geometry, lifetimes, bytes moved, proven-safe indices, error bounds…). A rewriter simplifies the graph without changing its answer. On the other side sit machine facts: the hardware described as abstract compute and placement facts (places with capacities and bandwidths, executors with their operations, movers, dispatch). Today these are TargetProfile records — the device query and calibration measurements, with fallbacks borrowed from another part’s measurement or keyed by compute capability; under ADR-0050 every fact also carries its source (queried, measured, declared, derived, nominal). Placement reconciles the two fact layers: it chooses where and how each piece of work runs — today by one rung rule per decision, under ADR-0050 by one evaluator and one search (§8). Only then is the result lowered to LLVM IR / PTX, which LLVM turns into an executable. The interpreter, which runs the graph directly, is the reference: a compiled result is correct when its flow of operations is the program’s dataflow and every value lies within the error bound stated before the run; bit-for-bit agreement with the interpreter is a development mode for testing (ADR-0049).

0.1 Philosophy

  • The language is the flow. A program states data and how it flows, data -> transform -> result;, not the control that moves it. A map says every cell is independent, a fold says how values combine, a binding says who reads what.
  • Data is category-theoretic. Values are objects, transforms are morphisms, a program is their composition. The compiler’s IR is that graph, and its rewrites are the category’s laws (spec/category-ir.md; §5).
  • Expressing the flow beats expressing control. Because the source states only what depends on what, the compiler derives what runs in parallel, what merges into one kernel, what stays in registers, shared memory or cache, and what moves between devices, from facts on the graph (independence, reuse, death points, footprints) against the hardware’s facts. Control written by hand fixes each of those decisions for one machine.

What follows from it:

  • Two kinds of facts, reconciled by the compiler. The dataflow’s facts (what each value reads, when it dies, what is independent) and the hardware’s facts as abstract compute and placement: where bytes can live, what computes (operations as shapes, with the place each operand must be in), what moves bytes, how work is dispatched — each fact measured, queried or declared, never a part’s name. Compilation places the dataflow on the machine with one cost model and one search, then lowers it; the few hardware-specific steps come last, kept minimal. A new chip, vendor or ASIC is described as facts, not given a new backend’s worth of heuristics (§8, ADR-0050; its first step is in progress — today rules over the same physical properties decide).
  • No runtime graph recording. Which work merges into one kernel, vertically along a chain and horizontally across independent branches, is decided at compile time from the dataflow. Nothing is traced or captured while the program runs.
  • Correct numerics: the flow and the bound, not bit-identity. Every result is within an error bound stated before the program runs (ADR-0040). The compiler orders and combines operations freely, so parallel sums may differ in the last bits between runs; bit-reproducible runs are a development mode (ADR-0049). Reduced precision is opt-in, per product.
  • Readable, idiomatic source. Programs read like the math they compute. If natural code compiles worse than a hand-shaped version, the compiler is fixed, not the program.
  • A language AI agents can write and verify. Deterministic semantics, precise diagnostics with stable codes, one formatter (mapal fmt), a language server, and the interpreter as an exact reference that any compiled run is checked against.

Two fact layers, one reconciliation — the idea to keep in mind. The program side and the hardware side are both written down as facts. Dataflow facts (§6, mapal-ir) say what the program needs: which cells are independent, what each one reads, how many bytes cross each edge, when a value dies, how large the error bound is. 2Language syntax — Mapal-Core in one sitting

Mapal programs are flows: values move left-to-right through steps joined by ->. There is no hidden control flow — the text you read is the dependency structure the compiler will use. This section covers Mapal-Core, the subset that compiles today (HANDOFF.md §4, docs/spec/user-guide.md), including the model-scale additions of ADR-0042…0048: math builtins, narrow storage, read, size-generic functions and types, top-level values (§2.10). Constructs outside Core still parse and are rejected with a precise P- or L-code diagnostic. A whole real program in this style: examples/llama.mapal (§11).

2.1 The smallest useful program

fn main() {
    1048576 -> iota -> ts;
    ts -> map { t -> t * 2 } -> doubled;
    doubled[1048575] -> println;

Read each line as a pipeline: make the range 0..1048576, double every element (in parallel — nothing says so, the graph proves it), print the last one. Bindings (-> ts;) name an intermediate so later flows can use it. A flow is a statement, not an expression: it routes a value; it does not itself produce one.

2.3 Bindings, mutation, element update

2048 -> hidden_size;      // top-level binding: program-wide, immutable, computed before the run
5 -> x: i32;              // immutable binding (flow form)
mut counter: i32 <- 0;    // mutable binding (assignment form)
counter + 1 -> counter;   // legal only because counter is mut
c[t] <- v;                // element update: "c with slot t replaced" (a fresh value in the IR)

Everything is immutable unless declared mut — there is no const keyword, and a top-level binding is never mut (L1801). Immutability by default is load-bearing: an immutable value can be read by any number of parallel branches safely, and a value whose dataflow reads no input can be computed before the program runs (§2.10). c[t] <- v looks like mutation but denotes a new array value in the graph (Update, §5) — whether it is stored in place is a backend decision guided by last_use_plan (§6).

2.4 Functions

fn clamp(v: f32, lo: f32, hi: f32) -> f32 {
    (v > hi) -> {
        -true->  hi;
        -false-> v;
    } -> ret;
}

fn main() {
    (270.2, 0.0, 255.0) -> clamp -> r;   // tuple input, one step
    r -> println;                          // 255
}
  • ret names the function’s output; ret.0 / ret.1 fill tuple slots. At most one full-value writer may reach ret (checked as T0101).
  • A function conceptually takes one input — a tuple when it has several parameters. This single-input rule is what keeps the graph uniform (§5).
  • Recursion is out of Core by design (L1008): cycles live in loop dataflow, never in the call graph. Iteration is written with loop (§2.7) or fold (§2.6).
  • main takes no parameters and declares no return.
  • Size-generic functions declare their sizes once after the name — fn project<tokens, rows, columns>(weight: Matrix<rows, columns>, x: [f32; tokens * columns]) -> [f32; tokens * rows]. There is no call-site syntax: the sizes are inferred from the argument types at each call, and lowering emits one fixed-size function per size tuple, so every later fact still sees concrete extents (ADR-0047).

2.5 Pipelines and shorthand stages

fn f(data: i32) -> i32 {
    data * 2
        -> + 5        // shorthand: piped value is the left operand
        -> ret;
}
// f(10) = 25

A shorthand stage like -> + 5 means “pair the piped value with 5, then add.” In the AST it is an OpShorthand stage whose expression contains a single Hole leaf for the piped value; in the IR it becomes an ordinary Pair + Add (§4, §5). Naming intermediates (-> s1;) changes nothing semantically — it only labels a graph node.

2.6 Collections: map, fold, and the pure builtins

(a, b) -> zip -> map { p -> p.0 + p.1 } -> c: [i32; 16];   // elementwise add
(0, c) -> fold { acc, x -> acc + x } -> total;              // sum, in order
16 -> iota -> ts;                                            // [0,1,…,15]
arr -> enumerate -> indexed;                                 // [(0,a0),(1,a1),…]
7 -> fill -> sevens: [i32; 4];                               // [7,7,7,7] (count from the type)
t -> widen_f64 -> wide;                                      // i32 → f64 (also widen_i64, widen_f32)
x -> to_bf16 -> stored;                                      // f32 → bf16, rounded once (also to_f16, to_f8e4m3, to_f8e5m2)
v -> sqrt -> root;                                          // math builtins: pipeline form only
angle -> sin -> sine;                                       //   (also cos, exp)
-x -> exp -> decay;
  • map { x -> … } applies an inline block to every element: [T; n] → [U; n]. The block may capture enclosing values (arrays included) — captures are broadcast to every element and recorded explicitly in the IR.
  • fold { acc, x -> … } threads an accumulator in index order: (Acc × [T; n]) → Acc. The compiler may regroup it — lane partials and a tree, split or walked pieces — where step_algebra / fold_tree_step prove the step is a combine whose order is free (§6). On the default face that includes float +, within the stated bound (ADR-0040, ADR-0049); the development modes keep source order.
  • The block is not a first-class function value; lowering turns it into a real (anonymous) function in the graph (MapBody / FoldBody).
  • Math builtins exp, sqrt, sin, cos are written only in pipeline position (x -> sqrt, never sqrt(x)). Each has a contract (its error bound), a reference definition written once from plain operations, and per-target realizations the target declares as capability data — a CPU’s correctly rounded sqrt, a GPU’s measured ex2.approx unit, an ASIC’s CORDIC unit or none. Among the realizations the contract admits, the cheapest is chosen; nothing reads a target’s name (ADR-0042, ADR-0046; mapal_ir::math::choose).

2.7 Choice and repetition: guards and loop

// Choice — a guard block. Arms are pure; only the taken arm computes.
op -> {
    -0-> a + b;
    -1-> a - b;
    -2-> a * b;
    -3-> a / b;      // does NOT run (and cannot trap) when op is 0
    -_-> a % b;      // default
} -> ret;

// Repetition — a loop is a cycle in the dataflow, steered by a guard.
mut k: i32   <- 0;
mut acc: f32 <- 0.0;
loop {
    (k < 4) -> {
        -true-> {
            acc + coeffs[k] * signal[4 + k] -> acc;
            k + 1 -> k;
            -> loop;          // back-edge: go around again
        }
        -false-> acc -> ret;  // exit edge
    }
}

Guard discriminants in Core: -true->, -false->, integer literals (-3->), and the default -_->. Pure guard blocks lower to a Phi (choose-one) step in the IR; which arm’s work is gated (skipped when not taken) is decided by guard_plan (§6). Both arms are always compiled; computing is what is conditional.

2.8 Fanout (parallel by default) and seq

6 -> {
    -> square -> sq;     // branch 1 — independent
    -> double -> db;     // branch 2 — independent, may run at the same time
}
// implicit join: both sq and db are available here
sq -> println;
db -> println;

Fanout branches are headless flows starting from the piped value. Independence is structural: if no branch needs another’s result, they are parallel — no keyword required. Effects (print) may not appear inside a fanout branch (T0201); they belong to the sequential “host spine.” A seq { … } stage is the opposite: an explicitly ordered statement block. It leaves no footprint in the IR — ordering there comes from data dependencies and the effect token (§5).

2.9 Effects, time, and precision annotations

"total = " -> print;      // raw, no newline
total -> println;         // with newline
() -> time -> t0;         // monotonic clock read (milliseconds, f64) — effectful, never reordered
"model.bin" -> read -> model: Model;   // raw bytes of a file → a typed value (annotation required)

(a, b) -> fold: tf32 | f32 { acc, k -> acc + a[k] * b[k] } -> s;
                          // ": compute" — products in this body admit TF32 operands (ADR-0041)
  • print/println, time and read are the effects in Core. In the graph they thread a linear IO token; for prints and clock reads that token pins their order (§5). A read takes the token too, but the token orders nothing it computes: the read is an independent task that starts when the run launches, and only its failure is ordered — delivered as a trap at the first checkpoint past it, in source order (ADR-0045 D8). read loads an array — or a whole struct of arrays, like a model’s weights — from a file; a relative path resolves against MAPAL_DATA_DIR; the array it yields is an ordinary immutable value (ADR-0045).
  • A : compute annotation (: tf32 | f32, : bf16 | f32) on a function, loop/seq block, or map/fold step widens the set of precisions its float products admit. Default is full f32 with an a-priori error bound (§6, precision_plan; §9.2).
  • Operators: + - * / %, comparisons == != < > <= >=, logic && || !, unary -. Division/modulo by zero and out-of-bounds indexing are traps (defined failures), reported in source order.

3AST — what it is and how it is created

The AST is a thin parse tree: syntax, names, spans, literal values, and flags — nothing more. It does no name resolution, no type inference, and no effect classification (crates/mapal-syntax/src/ast.rs). Think of it as the deserializer’s scratch space: faithful to the text, including its mistakes, so diagnostics can be precise. The program, for all later purposes, is the graph (§5).

3.1 Step by step

  1. Lex. lex(&str) produces tokens, each a kind plus a byte-range SourceLoc { start, end } into the original text. Token text is never copied — consumers slice &source[span] (single source of truth). Malformed literals yield L-code diagnostics but lexing continues.
  2. Parse. A hand-written recursive-descent parser builds the tree following the §2 grammar. Every node carries its span. On error it recovers (synchronizes to a plausible boundary) and records an Error node, so one run can report many problems — 34 P-codes in total (crates/mapal-syntax/src/parser.rs).
  3. Keep the rejected. Forms outside Core (function-call syntax f(x), ?, dynamic arrays [T], custom loop labels, pattern guards) are kept as dedicated node kinds with their diagnostic, rather than silently mis-parsed. Lowering’s job is then a clean “defined exactly on Core” partial map (§4).
  4. Merge + sort. Lex and parse diagnostics are merged and stably sorted by (span.start, span.end). The public entry is parse(&str) -> ParseOutput (crates/mapal-syntax/src/lib.rs).

4.1 What lowering does, in words

  1. Sizes and top-level values (rounds). Top-level bindings form a dependency graph; their scalar values are computed by the interpreter on a small synthetic program and become literals, so they can serve as sizes (ADR-0048 D3). A call to a size-generic function infers the sizes from its argument types; each distinct size tuple becomes one ordinary fixed-size function, so nothing downstream ever sees a size parameter (ADR-0047).
  2. Types first (A). Surface TyKind values are resolved to IR Ty values: named types are looked up and structs inlined, depth is bounded (MAX_TY_DEPTH = 64), and anything outside the Core whitelist is refused. The two Ty types are genuinely different types joined by this partial translation — do not conflate them.
  3. Effects + call graph (B). Which functions can (transitively) print or read the clock, and is the call graph acyclic? A recursive cycle aborts here with the teaching diagnostic L1008.
  4. Typing walk (D1). Each function body is type-checked; this pass collects many errors. Emission afterwards is fail-fast and assumes a well-typed-enough tree.
  5. Declare + emit (C, D2/D3). Each function gets exactly one input object and one output object. Scopes map names to objects; every computation step becomes one morphism built through the checked IrBuilder. Inline map/fold blocks become anonymous functions; captured variables become leading tuple components.
  6. Seal (E). The builder freezes the graph. From here on it is immutable; the only way to “change” it is to build a new one (which is exactly what the rewriter does, §7).

4.3 The two gates after lowering

  • validate (crates/mapal-ir/src/validate.rs) is an independent oracle: it re-derives every graph invariant from scratch without sharing builder code. The property “seal succeeded ⇒ validate finds nothing” is property-tested. It runs in tests/debug, not as a mandatory production pass.

It needs the tree as well as the graph, because fanout scope is precisely what lowering erased. This is the one place the tree is consulted after lowering; everything downstream sees only the graph.
5Category IR — the graph, in plain words

Forget the word “category” for a moment. The Category IR (CategoryIr, crates/mapal-ir/src/graph.rs) is a dataflow graph: circles are values, arrows are steps that compute a value. The categorical names stuck because the design borrows two ideas from that world — compose steps by matching output-to-input types and translate the whole graph with meaning preserved — but the data structure itself is ordinary Rust: three slotmap arenas with deterministic iteration order and no HashMap anywhere.

Vocabulary translation (the only category theory on this page).
Object → a value (with a type).   Morphism → a step: one directed edge source → target labeled with an operation.   Composition (f -> g) → plumbing: feed f’s output into g.   Product (A × B) → a tuple.   Functor → a translator (a backend) that maps the graph to another world while preserving the plumbing, hence the answer.   Trace → feedback: a loop.

  • IoToken is the linear “world” value threaded through effects. It may never be duplicated, stored in an array, chosen by Phi, or captured by a map/fold body — one shared predicate (ty_contains_token) enforces all token rules, deeply (it finds a token nested in ((IoToken, x), y)).
  • A function’s morphism list is an insertion-ordered set, not a schedule. Execution order is recomputed by topo_order (§6) whenever someone needs one — never stored, so it can never go stale.
  • Each float Mul also carries an admitted-precision set (default {f32}; widened by : compute) in a side table on the graph.

5.3 The rules the graph guarantees

These invariants (DESIGN “I-codes”) are what every plan silently relies on. In plain words:

  • One producer. Every non-constant, non-parameter value is written by exactly one edge (a LoopMerge excepted: one enter + back-edges). Dataflow dependencies are therefore exact — no alias analysis, no “may-def” guessing.
  • Typed plumbing. Every edge type-checks locally against its operation’s signature.
  • Tokens stay linear. The IO token is never duplicated or dropped, so effect order is structural.
  • Determinism. Arena storage iterates in insertion order; dumps, topo orders, and emissions are byte-stable across runs.
  • Sealed = trustworthy. Graphs can only be built through the checked builder and are immutable afterwards. Consumers never defensive-check structure the builder already proved.
6Plans — the facts deduced from the graph

A note on the title first, because it corrects a common first guess: plans are not built on the AST. The tree is discarded after lowering/checking. Every plan is a pure query over the sealed graph: fn plan(&self, f: FuncId) -> Plan on CategoryIr in crates/mapal-ir/src/algo.rs and algo/ (≈ 14,400 lines together — the intellectual center of the compiler), with byte and residency facts beside them (access.rs, residence.rs, unit.rs) and the numerics in split.rs, math.rs, narrow.rs. The authoritative one-line-per-fact list is the facts catalog in CLAUDE.md. “Code → plan” therefore means: source → graph → the fact the graph proves. This section is the central record of those plans, their algorithms, and who consumes them.

6.1 The four rules every plan obeys

  1. Facts live on the graph. Each fact is computed at most once per (graph, function) and stored in a pre-allocated OnceLock slot (crates/mapal-ir/src/facts.rs). Facts depend on other facts (path_plan reads loop_plan; tile_plan reads bounds_proof), forming a small dataflow of their own. A query reads the stored value; nothing recomputes per call site.
  2. Partial = safe. If a plan cannot prove its shape, it returns None / empty / false and the compiler takes the slow correct path. A plan can cost performance when silent; it can never change the answer.
  3. Machine-free. mapal-ir answers “is this legal, and what does it need?” (geometry, independence, bytes, lifetimes, proofs, error bounds). Whether it is worth it on a given machine is answered by placement, which reconciles these facts with the machine facts (§8). No chip name and no measured hardware number is stored in a plan; where a fact needs a capacity to answer (e.g. residence_plan: does this value’s working set fit a cache of C bytes?), the capacity is an argument, supplied by the machine side.
  4. One question each. New logic starts by checking this catalog. If a needed fact is missing, it is added here as one tested query — never re-derived inside a backend pass (AGENTS.md standing rule).

6.2 The catalog

Filter by text or by group. Each card states the question in plain words, the algorithm sketch, the consumer, and the fallback when the proof fails. Groups: structure order & loops · parallel tasks & gating · geometry kernel shapes · memory lifetimes & materialization · safety proofs & precision.

topo_order(f) -> Vec<MorphismId>structure

Question: in what single order could this function execute, respecting every dependency?

Algorithm
Kahn-style ready walk with a min-heap keyed by (loc.start, loc.end, insertion index) — source order, not compiler-construction order. That choice is observable: when two independent steps can both trap, the one earlier in your source is reported (§10).
Consumers
Everyone: interpreter walk, sequential emission, and as the position basis for last_use_plan.
Fallback
None — total on well-formed graphs (cycles only inside loop SCCs, handled by loop_plan).

sccs(f) · loop_structure(f) -> Vec<LoopScc> · loop_plan(f, merge) -> Option<LoopPlan>structure

Question: where are the loops, and for each one: what is the initial state, the merge point, the decide/advance order, and the exits?

Algorithm
Tarjan SCC over objects; an SCC containing a LoopMerge is a loop region. loop_plan then checks the canonical shape (one LoopEnter, shared condition Bool, exits leaving the region) and records init/merge/decide/advance/exits.
Consumers
Interpreter loop driver, rewrite replayer + loop lifting, both backends’ loop CFGs, path_plan, trip_split, last_use_plan (two-iteration liveness).
Fallback
None ⇒ the region is treated as opaque sequential work; never miscompiled.

path_plan(f) -> PathPlan (+ is_single_path)parallel

Question: what can run at the same time, as an explicit task DAG — and where must the sequential (effectful) world wait?

Algorithm
(1) Order by topo_order. (2) Set aside the host spine: token-touching steps (prints, clock reads) and effectful loops become ordered checkpoints. A file read is the exception (ADR-0045 D8): the Read and its array’s Proj form a task of their own with no inputs, which starts when the run launches; its failure is a trap delivered at the first checkpoint past it. (3) Bulk ops (Map/Zip/Enumerate/Iota/Fill) → Split tasks (element range sliceable); Fold → Seq task; each loop region → one Seq task; remaining scalars grouped by dataflow+co-writing connectivity (never mere sibling reads). (4) Dependencies = “the task that produced each input object” — direct dataflow is the complete relation. (5) Rank = critical-path weight, long poles first. (6) Checkpoints carry per-task watermarks (past-last-trap) or completion when the value is consumed.
Consumers
LLVM backend → one @taskN per task + static dep/rank table → mapal-rt work-stealing pool (§9, §10).
Fallback
Single-path (or malformed) plan ⇒ plain sequential emission.

guard_plan(f) -> Vec<GuardSite> (+ gated())parallel

Question: for each Phi (guard), which work belongs exclusively to each arm — and must that work be gated (not computed when the arm is not taken)?

Algorithm
Per-arm consumer closure (work whose every consumer is inside the arm), with loops joining as whole units via loop_plan. Transitive can_trap/heavy flags through nested sites. Legality first (can-trap must gate), then cost (heavy work gates; two scalar arms are left branchless).
Consumers
Interpreter (skip unchosen arm), LLVM + CUDA host emission (branch around gated work). Both arms stay in the binary.
Fallback
Not gated ⇒ both arms compute, Phi selects — correct only where both arms are total, hence the must-gate rule.

tile_plan(f) · tile_plan_strided(f) · tile_plan_radix(f) → TileSite / TileReadgeometry

Question: is this innocent “one result per element” map secretly a tiled kernel — neighboring outputs computed by lockstep folds reading broadcasts and vector runs?

Algorithm
(1) Skeleton: Map over iota whose body ends in exactly one Fold. (2) Coordinates from a t/C, t%C split (2-D) or the element itself (1-D). (3) Chain shape acc + x*y (either operand order). (4) Each read address decomposed affinely as base + ci·i + clane·lane + ck·k: clane=0 ⇒ broadcast, clane=1 ⇒ vector load, anything else ⇒ refuse. Strided/radix variants widen the coordinate reading (see radix_plan). TileKSplit records when the k axis itself may be split.
Consumers
CPU tiled micro-kernels (NEON/AVX/SME), GPU tile kernels (§9). Records geometry only — tile sizes come from TargetProfile.
Fallback
No site ⇒ ordinary elementwise map emission. Matmul, FIR, conv and attention shapes all match; there is no “matrix” concept in the recognizer.

cell_plan(f) → CellSite / CellRead (+ tree)geometry

Question: per output cell of a map, exactly what does it read — and is its fold step regroupable as lane partials + a tree?

Algorithm
Generalizes the tile reading per cell: affine reads with reach classification, independent cells across threads. CellSite::tree marks steps whose order is free (§6 fold_tree_step), enabling tree reductions where the float face permits (§9).
Consumers
GPU one-thread-per-cell / cooperative kernels; CPU cell kernels.
Fallback
No site ⇒ generic map path.

footprint_plan(f) -> FootprintPlan (of, rect, at)geometry

Question: for each consumer, what region of each producer does it actually touch?

Algorithm
Per producer→consumer edge, the touched footprint (rectangles / affine reaches with taps). This is the fact that replaces any “fusion pass”: whether work runs together, stays in registers/shared memory, or is stored follows from footprints + death points + the target (§9). Kernel boundaries are a result, never a pass.
Consumers
Backend work-unit formation, residency and staging decisions.
Fallback
Whole-array footprint ⇒ materialize and pass the buffer.

elem_plan(f) -> ElemPlan · map_law(m) -> Option<ElemSrc> (+ Outside)geometry

Question: what is out[i], as a closed function of i — can a consumer recompute (or directly source) elements instead of materializing the array?

Algorithm
Per array object, an ElemSrc law: element i expressed via sources, piecewise when every cell outside a row/range/column/single cell is a capture’s own element (the in-place range-map shape). map_law gives the same for one Map.
Consumers
Backends decide recompute-vs-store per target (GPU: usually recompute; CPU: vs L2 round-trip; FPGA: BRAM vs area) — the plan records legality, never the choice.
Fallback
No law ⇒ the array materializes.

row_fold(f) · whole_fold(f) → RowFoldSite / RowFoldOp · fold_tree_step(fold)geometry

Question: is this fold really “one row at a time” (or the whole function folded over one affine read) — and may its step be regrouped?

Algorithm
Recognize folds whose reads are affine in (row, k): softmax/decode and reduction shapes. fold_tree_step proves the step is an order-free combine (e.g. +/max under the admitted face), licensing lane-partials + tree reduction.
Consumers
Row kernels, split-K / tree-reduction emission.
Fallback
Sequential accumulator chain, exact source order.

move_plan(f) -> MovePlan / MoveSitegeometry

Question: where is data merely moved (transposed, gathered, re-laid-out) rather than computed — with what affine source pattern?

Algorithm
Sites whose element law is a pure affine re-indexing of one source. Backends traverse them in cache-blocked panels derived from TargetProfile geometry instead of element order.
Consumers
Transpose/pack/panel traversals on CPU; staging on GPU.
Fallback
Element-order copy.

emission_plan(f) -> EmissionPlan (class(o))memory

Question: which objects must actually materialize in emitted code — and which are just graph plumbing?

Algorithm
Classify each object: dissolved (products/views — no bytes, e.g. Pair tuples), inline (single-use scalar, emitted at its use), or named (needs storage), from consumer counts and kinds. Minimal emission: if it has no bytes in the semantics, it gets no bytes in the binary.
Consumers
All backends (naming, SSA/alloca decisions); CUDA minimal-emission path.
Fallback
Named ⇒ allocate; always safe.

last_use_plan(f) -> LastUsePlan (position · death · escapes · carried_by · dead_after, view variants)memory

Question: for each value, where is its last read — does it escape into the output, is it carried around a loop, and after which step is its storage free?

Algorithm
Positions from topo_order; death = max position over consumers; carried_by marks values crossing a LoopBack (live across two iterations); view-aware variants track dissolved products to their storage. Lifetimes are exact because every read is an edge.
Consumers
Buffer coloring/reuse (arena), in-place Update, free-at-back-edge, host↔device retention (§9). This is Mapal’s “memory model”: no GC, no ownership annotations — last-use is the lifetime.
Fallback
Escaping/unknown ⇒ keep alive to function end.

write_delta(f) → per-object Deltamemory

Question: for a loop-carried array, what contiguous range does each trip actually write?

Algorithm
Chase Updates and piecewise map laws around the loop to a per-trip written interval. A partial update then moves/retains only the delta across host↔device or iterations, instead of the whole array.
Consumers
Residency/retention, delta copies, cache decisions.
Fallback
Whole array is the delta.

trip_split(f) -> Vec<TripSplit> (TripPhase)structure

Question: for a counted loop, what trip intervals do guards on the counter cut out — which state is recurrent in each, what work sits outside, and can all-but-last trips of the first interval be skipped?

Algorithm
Counter-guard analysis over the loop_plan: phases with their recurrent slots, batched row writes, and the skip fact. Turns “loop with cases inside” into “phases the backend can schedule separately.”
Consumers
Loop emission (phase splitting, batching).
Fallback
One phase = the whole loop, guard evaluated per trip.

bounds_proof(f) -> BoundsProof (proven(m))safety

Question: which Index/Update steps are provably in bounds, so their trap guard can be dropped?

Algorithm
Affine/range reasoning over index expressions against static array sizes (iota-derived indices, div/mod decompositions, counter ranges). Only proven guards drop — “which bounds checks are provably unnecessary, and only those.”
Consumers
Guard elision in LLVM + CUDA emission; also read by tile_plan/path_plan (trap capability feeds watermarks).
Fallback
Unproven ⇒ keep the check; the trap remains possible and ordered.

precision_plan → set · round_at · cross · bound · exp · math · narrow · store (+ mapal_ir::split; ADR-0040…0044, 0046)safety

Question: which precisions does each float product admit, where may a value be rounded (once, at its producer), which edges must a rounded copy not cross, and what is each tile site’s a-priori error bound?

Algorithm
From the per-Mul admitted sets (innermost : compute wins): propagate rounding points to producers, mark edges a rounded copy would corrupt, and compose the weakest-member bound per site. Default face: full precision + bound + unspecified order, fastest on the native CPU+GPU; exact/contract faces are opt-in (§9).
Also
Each math builtin’s form and contract (math, exp); each narrow rounding’s form (narrow) and whether one format embeds exactly in another (the tensor-core admission over narrow storage); store: an f32 array read only by bf16-admitting products is stored rounded once by its producer. mapal_ir::split prices split realizations of a full-f32 product on a matrix instruction (two or three narrow parts per operand, ADR-0044): a coefficient admitted only if it meets the default face’s bound at the site’s K.
Consumers
Tensor-core eligibility (TF32, 16-bit, split forms), narrow storage, the choice of math realizations, value gates in tests (check the bound, not bit-equality, on the default face; mapal run --interp --bound prints the composed bound).
Fallback
{f32} everywhere — no rounding, bound is the f32 one.

radix_plan(f) → RadixFormgeometry

Question: is this integer really “digits” of the inputs — (x ÷ s) % r with constant divisors?

Algorithm
Recognize constant div/mod digit decompositions per object. Map/fold reads affine per digit then become tile sites over (i, lane, k) — the implicit-GEMM reading that lets convolution-shaped index arithmetic reuse the tile machinery.
Consumers
tile_plan_radix → tile kernels for conv/window shapes.
Fallback
Plain integer arithmetic, ordinary addressing.

static_plan(f) -> StaticPlan (fixed · roots → StaticRoot · Realize; ADR-0048 D3)structure

Question: which values can be computed before the program runs — and is it worth embedding them?

Algorithm
A value is computable when it depends on no input slot (unchanged_plan.inputs = 0 — the IO token counts as an input), its cone reads no file, and a loop is taken only whole. The roots are the computable values a run-time value reads. Each root carries its bytes, cells and the interpreter’s work over its cone; the rule weighs bytes against work: Embed (≤ 1 KiB, ≤ 2²⁰ steps, more steps than cells, no closed-form element law), Attempt (an uncounted loop, 2¹⁸ steps), else Compute.
Consumers
fold_static (crates/mapal-rewrite/src/statics.rs), before the rewriter; OFF arm --static=off.
Fallback
Compute: the value is computed at run time, once, where the other facts place it.

unchanged_plan(f) (trip · same · inputs) · call_keepmemory

Question: what is unchanged since last time — per loop-body array, which cells may differ from the previous trip; which values are equal on every trip; which input slots each value depends on; and per call site, which callee inputs are the same at every execution?

Algorithm
write_delta carried through row-local maps (row folds, per-row scales, projections, windows) as Rows / Pieces / Top; equal-every-trip values; input-slot masks. call_keep reads the callee’s masks at each site.
Consumers
Retained cells and gathered rows: a decode loop written without a cache, recomputing every position each trip, gets one from this fact — only the changed rows are recomputed (func/retain.rs, func/resident.rs; benches/results/evidence/local-rtx-5080/caching-memory.md). Values the same on every trip are made once; retain-call.
Fallback
Everything recomputed and moved every trip.

access_plan (reads · writes · class · edges) · residence_plan (at → Chip | L2 | Dram)memory

Question: how many bytes does each step read and write, which steps conflict (read-after-write, write-after-read, write-after-write) within a loop trip — and where do a value’s bytes live between their producer and their last reader?

Algorithm
access_plan: bytes through Pair/Proj views, storage classes (a carried slot’s views, an Update with its array), hazard edges per trip — the order device work is placed from. residence_plan: the peak live bytes over a value’s interval against a cache capacity the machine side supplies.
Consumers
Device placement by bytes moved, whether a GPU operand is read from DRAM or L2 (MAPAL_SITE_COLD trials, evict-first loads), the cost terms in §8.
Fallback
Whole-object bytes; DRAM residence.

unit_plan (UnitGroup) · stream_plan (StreamGroup, roles)geometry

Question: which tile sites, folds and cells reading the same rows can run as one unit with their rows kept on chip — and which of those groups can stream, as one pass over windows of an axis?

Algorithm
unit_plan: row-block groups whose every edge stays inside its rows; on-chip row buffers colored by death. stream_plan: a group whose tile folds over an in-group row’s cells — scores → softmax → weighted sum, i.e. attention — each member with a role (Produce, Cell, Fold, Consume, Row), each fold’s combine and each per-row value’s law from fold_combine, guard sides (a causal mask through a positions array) decided per window. Axis-wide values are never stored.
Consumers
The streamed (“flash-style”) attention kernel, on tensor cores for 16-bit operands; causal window skip; bf16 key/value windows.
Fallback
Each member its own launch; rows stored between them.

fold_combine (DepLaw::{Factor, Shift, Rescale, Phase}) · step_algebrageometry

Question: if a fold is cut into blocks, how do the blocks’ partial states combine — and what happens to values that are constant along the fold’s axis?

Algorithm
The state combines by the fold’s own operator. A value constant along the axis enters by a law: a factor applied once after the combine, a shift of a max/min, a rescale (it enters only as exp(κ·(x − v))·y: each block takes its own shift and is rescaled when combined — the online-softmax law, ADR-0042 D7), or a phase (it needs the partials combined first). step_algebra: product–accumulate pairs that may be one FMA, and fold steps that may regroup as lane partials + a tree — one realization rule shared by host and device.
Consumers
Row slices, split-K, stream-K walks, streamed attention, FMA contraction.
Fallback
One block, in order.

tensor_form · tile_plan_post (TilePost) · tile_plan_narrowgeometry

Question: is a tile operand a dense tensor whose panels are rectangular boxes; what does the cell compute after its fold (an epilogue); and which operands are exact widenings of 16-bit storage?

Algorithm
tensor_form: the operand as a ≤ 3-axis tensor over (row, lane, k), and whether boxes tile it exactly (what a bulk-copy engine such as TMA can fetch). tile_plan_post: the residual, scale, mask or per-row divisor after the fold, derived from the body, ending possibly in the stored rounding. tile_plan_narrow: each read’s storage format and bytes.
Consumers
Tensor-core tiles and their copies, epilogues computed in the tile instead of a separate pass, operand traffic in the cost terms.
Fallback
No box: lane copies; no epilogue: a separate cell map; f32 operand bytes.

trap_cell_plan (CellSite::traps)safety

Question: which maps are refused as device cells only because an index could not be proven in bounds?

Algorithm
The cell_plan refusals whose only reason is an unproven Index. Such a map runs on the device anyway: each cell checks its index, a failure is recorded in a module word, and the trap is raised at the next host checkpoint — a print, a clock read, a host trap, the exit, or a device-to-host copy, the only ways a device value reaches the host (rung device-trap).
Consumers
GPU cells; the runtime’s checkpoint hook (mapal_rt_checkpoint_hook, mapal_gpu_trap_arm).
Fallback
The map stays on the host.

Supporting queries you will meet in the source: func_objects (a function’s object set) and per-function trap capability (can this function trap, transitively?) — both stored facts feeding the plans above. Deep dives with line references: docs/architecture/deduced-queries.md.

8Reconciliation — placing the dataflow on the machine

Sections 5–7 built one side of the picture: a graph and the facts it proves. This section adds the other side — the hardware, written down as facts of the same kind — and the compile phase that brings the two together. The design is ADR-0050 (“the machine model”); the idea in one sentence: compilation places the dataflow on an abstract machine by one evaluator and one search, and only then writes the target’s language. Which work runs on the host or the device, which instruction computes it, how it is tiled and walked, where each operand lives and how it gets there — all of that is placement, and placement is a phase of compilation like typing or lowering, not a set of choices hidden inside kernels or tables.

Status, honestly. ADR-0050 was accepted on 2026-11-26. Step 1 — GEMM-shaped (sum-of-products) tile sites on the GPU — is in progress: its first commit (C1, 30f1a32f) added the target-agnostic crate crates/mapal-place — machine facts with provenance, the schedule, the evaluator, reuse by distinct bytes and an exact LRU simulator — but it depends on no other workspace crate, nothing depends on it, and no placement decision reads it yet. When it lands, it sits behind the switch machine-place, off by default until a measured confirmation turns it on. Until then, and as its OFF arm afterwards, placement is decided by today’s rung rules: per-decision rules that already read physical properties rather than chip names (crates/backends/llvm/src/rules.rs, §9.3). 8.1 Two fact layers

Dataflow facts — what the program needs

Deduced from the sealed graph by mapal-ir (§6): which cells are independent, what each cell reads and with what geometry (tile_plan, tensor_form), how many bytes cross each edge and conflict per loop trip (access_plan), when each value dies (last_use_plan), which work can run as one unit (unit_plan, stream_plan), how partial results combine (fold_combine), and how much error each product may carry (precision_plan).

Machine-free: the same facts for every target. Checked by property tests over generated programs.

Machine facts — what the hardware offers

The target described as abstract compute and placement facts: places where bytes can live, executors and the operations they run, movers that carry bytes, and how work is dispatched (§8.2). Nothing in them is a chip name or an instruction-set version; a new part is a new set of facts. Under ADR-0050 each fact says where it came from: measured, queried, declared (by a spec, RTL parameters, a simulation), derived or nominal, with an interval (mapal-place’s Src).

Today these live in TargetProfile (crates/backends/llvm/src/profile.rs): the device query plus the calibration line of benches/gpu/calib.cu for native-gpu, with no provenance per value — an uncalibrated part borrows the RTX 5080’s measurements, and some fallbacks are tables keyed by compute capability (§9.1). ADR-0050 translates them by Machine::of(target), marking each borrowed value as derived.

Placement is the phase whose job is to read both. That is the separation the project has been heading toward since its first optimization rule: “Optimizations derive from Mapal dataflow facts … + TargetProfile hardware facts” (CLAUDE.md, standing rules) and “hardware is physical properties, never a name or version” (2026-11-20). ADR-0050 takes the last step: the decision itself becomes one model over both layers instead of many rules.

8.2 The machine facts

Four kinds of fact describe any target, CPU, GPU, accelerator or a design still being synthesized. Each target sets the depth of its own trees; nothing below assumes a GPU (ADR-0050 D2).

Places — where bytes can live

A graph of instances (a tree is the common case): registers, shared memory, tensor memory, an ASIC’s SRAM banks, each L2 partition, a NUMA node, the host’s memory. A place has a capacity; a scope — the executors that reach it, by reach edges carrying bandwidth, latency and transaction size; a banking rule; and a management: explicit (the program addresses it) or cache. A cache also lists its instances, which executor or address maps to which, whether a line read through two instances is held twice, and its measured hit-against-distance curve — how many distinct bytes it really keeps for a cyclic, rotated or strided pattern, never the nominal size. Splits the schedule chooses (shared memory against L1) are places too.

Executors — what computes

A tree of the target’s depth (device → units → sub-partitions → groups → lanes). Operations are rows of geometry owned by some executor level: the shape (m, the set of n, k, batch), the operand and accumulator formats, each operand’s home place, its allowed layouts and which lane holds which element, latency and how many may be in flight, the measured rate and efficiency curve, and the accumulator’s numerics (ADR-0043). A scalar FMA is the 1 × 1 × 1 row; tensor-core instructions, a CPU vector FMA, an SME outer product and a systolic array are rows of the same table (below).

Movers — how bytes move

Program-issued copies (lane loads, cp.async, bulk-copy engines such as TMA with their box shapes, swizzles and multicast), hardware-issued ones (prefetch streams: what starts them, how far they reach), and links between machines — host ↔ device, with the rate by source (pinned or pageable) and the copy engines. Per-access cache policies (evict-first, persisting windows) are mover options.

Dispatch — how work reaches executors

A unit’s resources as capacities — so occupancy is derived from a schedule’s footprint, never a constant; which grid index lands on which unit; how a grid’s blocks start (all at once or staggered, measured); launch modes (plain, dependent overlap, cooperative, cluster) and their costs; barriers; atomics as a resource at the place that resolves them; the zero pass; the clock the part sustains under load.

8.3 The reconciliation: a schedule, one evaluator, one search

For each site (step 1: sum-of-products tile sites; later every cell, fold and streamed unit) placement produces a schedule (ADR-0050 D3):

Schedule partWhat it fixes
Executor subtreeHost, device, or both.
Operation and operand rolesWhich row of the operation table computes it, and which input plays a and which b (a transposed product is a role swap).
LevelsAny number of loop extents, each bound either to an executor level (parallel: blocks, warps, lanes) or to a place (sequential blocking: a CPU’s register tile, L1 and L2 panels).

Feasibility = every place’s footprint fits its share ∧ the numerics admit it (the operation and its number of pieces — 1, S, or unbounded for a walk — are within the site’s a-priori bound, ADR-0040/0041/0043/0044) ∧ the lowering can emit it. Then one evaluator prices every feasible schedule the same way (ADR-0050 D4):

TermWhat it counts
computeThe busiest unit’s work — ⌈tiles / slots⌉: full waves and the tail — at the operation’s measured rate and efficiency, at the sustained clock.

One search (D5) generates candidates bottom-up from the facts — operations the precision set admits, group tiles whose footprint fits the operation’s home, block tiles and depths within capacities for every feasible occupancy, traversals and launch modes — and prunes by admissible lower bounds (peak compute; every operand read once) and dominance. The top candidates go through a post-lowering gate: the code generator’s real registers and spills; a spill makes a candidate infeasible and the next one is taken. Facts with intervals are evaluated at both ends; a pick that flips inside them is marked open. The model’s error band is itself a fact (replay residuals): a new schedule replaces the incumbent only beyond it, so a re-measured rate does not churn the emitted code.

8.4 After placement: lowering, then a minimal target-specific step

A lowering emits any feasible schedule of the kinds it declares, and declares its constraints, its instruction counts and its footprints (D6). Layout is in the model (its bank-conflict cost is a fact); only the bit encoding is the lowering’s. What cannot yet be a machine fact — a code generator’s register-allocation quirk, a driver fault’s workaround, an index-width or unroll flag — is a separate step after lowering, keyed by properties and listed with why it is not a fact yet and what would make it one (the planned docs/target-specific.md; that list must shrink over time and must not grow per target). Each site’s schedule, predicted time, terms and any open flip are written into the module as a ; mapal.place line (D8), next to the existing ; mapal.ptx capability line.

8.5 How it helps — with this project’s own evidence

Interactions are priced, not patched

Today about seventeen decisions — placement, kernel kind, tile shape, staging, combine and split, raster order, the walk, epilogue and kernel boundaries, the zero pass, residency, concurrency — are each made by their own rule, in a fixed order, each reading the subset of facts it was written for (304 cited measurements over 68 rung names in rung_replay.tsv). The mma-walk rung (2026-11-25) priced how full the SMs were but not where the operands live while the walk scatters their readers: the L2 fact (l2_keep_bytes) existed, outside that rule’s view, and the walk lost — ×1.21 on the RTX 3090’s suite row, ×1.04 on the A100’s down projection (788 against 761 µs a layer; benches/results/evidence/hopper/disasm-rented.md). The fix added the fact to that one rule (MmaWalk::walk_bytes, b3ad75f4). ADR-0050’s design check then found that rule counts requested bytes where a cache evicts on distinct bytes. By the model’s count — an exact LRU simulation, not a measurement (the rented boxes had no profiler counters) — the RTX 5080’s 3072 × 4096 × 8192 product requests 1685 MB against 124 MB distinct, so the rule refused that walk for a reason the simulation does not support. The measured times there favoured refusal anyway (ordered 1836 µs against the walk’s 1829 µs + a 39.8 µs zero pass): a wrong reason, not a wrong pick. In one evaluator, reuse distance is one term every traversal pays.

A new target is a translation and a lowering

Because placement reads only machine facts, adding a target means writing Machine::of for it and a lowering — AMD (MFMA, LDS, 64-lane wavefronts, Infinity Cache, per-XCD L2s), CPUs (cores, vector units, cache levels, prefetchers, SME), ASICs (PE arrays, SRAM banks, a network-on-chip). A synthesis target is a machine template with free parameters (array dimensions, SRAM sizes and banks, NoC width) and a resource budget (area, DSPs, BRAM, LUTs, fmax): the same search ranges over the template’s parameters as well as the schedule (D7). Today the tile-shape ladder carries built-in assumptions — two resident blocks per SM (GPU_RESIDENT_BLOCKS), half the register file, powers of two — and parts without a measurement borrow the RTX 5080’s numbers; under ADR-0050 occupancy is derived and a missing fact is visible.

Every decision is explained in the output

The ; mapal.place line states the chosen schedule, its predicted time and each term. A reviewer can see why a site walks instead of running an ordered grid — say, because the ordered grid’s movement term exceeds the walk’s combine term — without rerunning anything. Today the explanation is spread over rule comments and replay lines.

Measurement checks the model; it does not choose the answer

Today a site may carry several candidate kernels (--cands, candidate 0 being the rules’ plan) and the GPU runtime can time them in trials and remember the winner per device (“wisdom”, crates/mapal-rt/gpu/mapal_choice.h). On noisy rented parts that loop reverted good picks (the A100’s ±50 % noise, docs/sessions/2026-11-26-readable-llama-and-five-gpu.md). Under ADR-0050 a measurement is a replay line in place_replay.tsv: a realized time outside the predicted band is a finding — a missing machine fact or evaluator term, fixed in the model, never a per-site override. A run-time confirmation, where kept, chooses only among the top candidates and only on pairs that differ beyond the null.

The bound frees the order — so the search space is large

ADR-0049 made correctness “the flow and the bound”: the compiler may order, split and combine freely, including atomics and stream-K walks whose order depends on arrival, as long as every value stays within the a-priori bound (ADR-0040 D2). That turns split-K, stream-K and hybrid traversals into ordinary points of the schedule space, admitted by a numerics fact (how many pieces the site’s bound allows; ADR-0044’s split coefficients) rather than refused to reproduce bits.

It must win back the earlier single model’s losses

An earlier single cost model, plan-cost (site_ns), already priced the scalar tile site; it measured mixed — it lost 2.7× on mm_1x1024x4096 on the RTX 4090 — and ships off. ADR-0050 is held to naming the term plan-cost lacked and winning those rows back (the replay corpus is seeded with them).

Not new on its own: dataflow languages (SISAL, Id — the 1980s and 1990s), size types (Futhark), separating the algorithm from its schedule (Halide), analytic mapping onto accelerators (Timeloop), floating-point error analysis (FPTaylor).

New — the combination: (1) the language’s meaning, the compiler’s facts and the hardware’s facts are one connected system; (2) the program states its numerical bound, which frees the compiler to choose any order and any realization within it, tensor cores included; (3) placement is derived from that system, not written by hand, tuned by measurement or learned, so a new target is a translation, not a new backend’s worth of heuristics.

9.1 TargetProfile — machine facts as data

crates/backends/llvm/src/profile.rs: one record per part — CPUs (generic, apple-m, apple-m4-sme, zen3, raptorlake, x86-64-v3, auto-detected native) and GPUs (rtx-3090, a100, cuda-ada (an RTX 4070 Ti box), rtx-4090, h100, h100-pcie, rtx-5090, rtx-5080, and native-gpu = the device query plus the calibration line of benches/gpu/calib.cu, read from MAPAL_GPU_CALIB, the user cache, or the repository). It holds hardware facts — L1d geometry (sets/ways/line), L2 size, vector width, matrix-unit shape, measured dispatch economics, and for GPUs: SM count, schedulers, warp size, shared-memory budget, MMA/WGMMA capability, copy costs — and some fits of particular Mapal kernels (DeviceCost). Derived helpers (tile_i, move_block, gpu_tile, pack_pays, device_pays, raster…) turn facts + a site’s extents into concrete constants. Where a part has no measurement, today’s code mostly prices it anyway: the RTX 5080’s measured cycles at this part’s clock and SM count (coop_body_cycles, chain_cost, the plan rates — “derived, never unpriced”), or tables keyed by compute capability (barrier cycles Gpu::bar_cycles, FP32 lanes per SM fp32_lanes_of_cc, matrix rates). No value records which of these it is; ADR-0050 makes that provenance a fact (§8.1).

Geometry ports; constants are derived from properties. Which reads broadcast, which axes split, what may interleave — deduced once, backend-independent (tile_plan, path_plan). Tile factors, panel depths, unroll counts, task grain — derived from a cache hierarchy’s and a register file’s physical properties, not switched on a part’s name: “a new chip is a new property set, not a new code path” (CLAUDE.md, 2026-11-20). Two exceptions remain today: fallback tables keyed by compute capability, and the RTX 5080’s numbers borrowed by parts nobody calibrated (§8.5). ADR-0050 goes one step further: the constants are not computed by one rule each but chosen together, by the evaluator of §8, and a borrowed or nominal value is marked as such.

9.2 The CPU path (LLVM backend)

Entry: emit_detailed(ir, &EmitOpts) -> Emission { text, device, profile_name } (crates/backends/llvm/src/lib.rs). Emission is a pure function of (graph, options, profile) — same triple, same text. Per function, the emitter (src/func/: core · frame · drive · ops · tile · window · conv · packed · trio · vec · bulk · sme · hostpar · calls; GPU: gpu · flow · stream · resident · retain · rowfold · horizontal · zero) walks the plans:

  1. Frame + storage (frame, reuse.rs): emission_plan decides what gets an alloca slot vs dissolving to SSA; last_use_plan colors buffers so dead storage is reused; frame aliases let an Update whose source dies here write in place.
  2. Scheduling (drive): if path_plan is not single-path, emit one @taskN per task + the static dependency/rank/checkpoint tables for mapal-rt (§10). Before dispatching, a roofline test asks whether the task can pay for its own dispatch (max(flops/rate, bytes/rate) vs measured dispatch_ns); one-slice tasks run on the calling thread. Otherwise emit plain sequential code in topo_order.
  3. Kernels (tile · packed · window · conv · vec · bulk): a TileSite becomes a register-blocked micro-kernel nest — pack the strided operand into panels (only when pack_pays: working set > L2), block for L1/L2 from profile geometry, keep accumulators resident across k, store once. The innermost leaf differs per part (scalar FMA / NEON / AVX / ARM SME fmopa into ZA tiles); the nest around it is shared. MoveSites traverse in conflict-avoiding panels; window/conv sites reuse the same geometry with tap reads.
  4. Loops + guards (loops.rs, trio): loop_plan → a CFG with phis for carried state; guard_plan.gated() → branches around gated arm work; bounds_proof → omitted trap branches. Traps that remain call the runtime trap path with the source-order index (§10).
  5. Hand off to LLVM. The emitted IR is deliberately shaped for LLVM to derive the schedule: accumulators as SSA so SROA keeps them in registers, affine accesses so the vectorizer and LSR fire, FMA contract flags on the default and contract faces, never on --exact. clang -O3 does the rest (≈ 99% of compile time).
Expand: numerics — the default face and the development modes

Correct means the flow and the bound (ADR-0049): a program is correct when its flow of operations is the program’s dataflow and every value lies within the a-priori bound stated before the run. The compiler orders, splits and combines freely — atomics, split-K and stream-K included — so the last bits may differ between runs and between targets. Bit-for-bit modes remain, as development modes for testing and debugging, never as a language promise and never as a goal the compiler optimizes for.

9.3 The GPU path (NVPTX device module + host orchestration)

The GPU leg reuses the same LLVM backend: device-suitable sites are emitted as an NVPTX module (PTX text embedded beside the host IR), and the host code launches them. This is the one place physical location is real — host vs device are different places, and every host↔device copy is a typed, costed transmission the facts must justify.

  1. Placement. For each candidate site (tile/cell/row-fold/streamed unit/bulk), device_pays compares estimated device time + required copies against staying on the host, using footprints, extents vs SM count, and whether operands are already resident. A per-trip cell is placed where it moves fewer bytes a trip (bytes-place); a map one of whose operands a placed site makes is a candidate too, so a chain is decided whole (cand-made) — which is what keeps a whole decode step on the device. Unplaced work runs as CPU tasks: a program is CPU-only, GPU-only, or mixed, per site.
  2. Residency + arena. last_use_plan, write_delta, unchanged_plan, access_plan and residence_plan deduce, per object (loop-carried state included), where it lives, what is reused, and what is retained across launches. Equal weight views are one object, so a model’s weights upload once; a prompt writes its key/value rows in place on the device and the decode loop takes those buffers (once-range, carry-take). Buffers are lifetime-colored in a device arena; any copy or allocation the dataflow facts do not require is treated as a bug (a “finding”), never a default. Partial loop updates move only their delta.
  3. Kernel formation (the flow rung). There is no fusion pass and no run-time graph capture. Work units follow producer/consumer footprints, death points, and cell independence, merged at compile time along a chain and across independent branches (func/flow.rs, func/horizontal.rs): a value with several readers is computed once; independent cells spread across threads; folds with a proven tree step become lane partials + warp-shuffle trees. Kernel boundaries fall out of where values must materialize.
  4. Streamed attention. stream_plan + fold_combine’s rescale law turn scores → softmax → weighted sum into one pass over key windows with a running maximum (the “flash attention” shape), derived from facts rather than recognized by name (func/stream.rs). A causal mask skips whole windows (with a run-time finiteness check where the skipped values are only known then, rung finite-check); 16-bit windows fold on mma.sync.
  5. Kernel leaves. Per site geometry: thread/block tile, shared-memory staging (cp.async rings), register accumulators. Tensor cores where precision_plan admits them: TF32 mma.sync under : tf32 | f32; 16-bit mma.sync.m16n8k16 with f32 accumulation over bf16/f16 operands (bf16 weights against f32 activations included); split forms of full-f32 products within the default bound (ADR-0044). On Hopper, wgmma (TF32 m64nNk8, 16-bit m64nNk16) fed by whole-tile TMA boxes with warp specialization: producer warps issue the copies, consumer warpgroups the products. Traversals: rasterized ordered grids (gated by b’s re-reads past the L2 keep), split-K, stream-K priced by the part’s rates (streamk_priced), and mma-walk — the 16-bit tensor tile walked over every SM’s matrix pipe; its operand re-reads are now priced against the L2 keep (walk-reuse, b3ad75f4), the case §8.5 retells.
  6. Device traps. A map refused as a device cell only because an index is unproven runs on the device anyway (trap_cell_plan): each cell checks its index, a failure is recorded in a module word, and the trap is raised at the next host checkpoint — a print, the clock, a host trap, the exit, or a device-to-host copy (rung device-trap).
  7. Rungs — today’s reconciliation. Each GPU decision is a named rung in GpuRungs (crates/backends/llvm/src/lib.rs) decided by a rule in rules.rs that reads the site’s fill and face and the part’s physical properties — FFMA per DRAM byte, registers per resident thread, L2 per SM and the L2 keep, matrix rates, measured launch and copy costs, capabilities as geometry (Caps: matrix operations, copy engines, evict-first loads, the PTX ISA each needs) — never a part’s name or version. Every cited measurement is a replay line (rung_replay.tsv, test rung_rules_replay); --gpu-off=/--gpu-on= are measurement flags. A site can carry a table of candidate kernels resolved when the module loads; candidate 0 is the rules’ plan, and the runtime may time the others and remember the winner (mapal-rt/gpu/mapal_choice.h). This rule chain is what ADR-0050 replaces (§8) and keeps as its OFF arm.
  8. Lowering. LLVM NVPTX emits PTX; each device module declares the largest PTX ISA its capabilities need (; mapal.ptx, checked by a ptxas preflight); ptxas/driver produces SASS. What LLVM must derive (vector widths, unroll, FFMA contraction…) is declared up front per rung and then checked in the realized PTX/SASS — see the evidence pass below. One known workaround that is not a fact yet: warp-specialized kernels launch alone, because a merged launch crashed (root cause open, docs/sessions/2026-11-26-readable-llama-and-five-gpu.md).

The older standalone CUDA-text backend (crates/backends/cuda/: host emitter + kernel emitter + arena) remains as the host-form reference; new device work lands in the NVPTX leg. The Verilog backend (crates/backends/verilog/) is the planned third translator — the same graph to clocked hardware with a done-protocol — evidence that the dataflow model reaches past SIMT machines.

Expand: the evidence pass — how optimization decisions are kept honest

No keep/remove/gate decision stands on timing alone (AGENTS.md). For every optimization or codegen change:

  1. Intent, before measuring. Declare machine-checkably what LLVM/NVPTX must derive from the emitted IR, which PTX/SASS features must appear/disappear (instruction mix, vector widths, FFMA-per-load, registers, spills, occupancy, launches), and what data movement the facts require per program and per loop trip.
  2. Realized. Collect LLVM optimization remarks, PTX, SASS (cuobjdump/nvdisasm), and ptxas -v for every measured kernel/arch; check against intent. A mismatch is a finding, never a pass. Library kernels (cuBLAS/CUTLASS) are captured from the actual launch.
  3. Explain. Every decision-driving timing difference cites the SASS/usage difference that explains it. Unexplained ⇒ the decision stays “open.”
  4. Breadth + genericity. Judge on the multi-workload suite (GEMM/MLP, attention/softmax, reductions, FIR/conv/window, elementwise chains, fan-in/out, loops; CPU-only, GPU-only, mixed) against the best library or PyTorch — and validate every rule on unseen generated programs (values vs oracle/bound, plus movement/kernel intents). Benchmarks are acceptance only; programs are written idiomatically and never reshaped to flatter the recognizer. Tooling: benches/gpu/intent.py, evidence.py — a GPU run without its evidence.tsv is not a result.

10Runtime & execution semantics

10.1 The thread pool (mapal-rt)

Compiled parallel programs link mapal-rt (crates/mapal-rt/src/lib.rs), a work-stealing pool executing the static task table the backend emitted from path_plan. Tasks unlock as their producer dependencies retire; Split tasks slice their element range across lanes; ranks schedule long poles first. MAPAL_PAR sets total executors including the host thread (MAPAL_PAR=1 is the sequential lever). Hard-won details, all measured: dispatch wakes only the lanes it filled; the completion path is lock-free; the host spins briefly before parking while workers do not (spinning workers measured worse and were removed).

Programs with device work also link the GPU runtime (crates/mapal-rt/gpu/mapal_gpu.c, CUDA driver API): it loads the module, resolves each site’s candidate table and its pick at load time (off the timed path), keeps the device arena, and launches. On a machine without a GPU the same calls run on a host emulation (mapal_gpu_emu.c), which is how the tests drive the shipped decision code.

10.2 Checkpoints, watermarks, and trap order

  • Effectful steps (prints, clock reads) run on the host in program order. A file read is not pinned (ADR-0045 D8): it is a path_plan task that starts when the run launches, beside work that does not read it; a failure zero-fills its array, is recorded at the read’s position in topo order and is delivered by the first checkpoint past it. (A read left on the spine — inside an effectful loop, in a sequential function or on a GPU build’s host — is a checkpoint like a print.) Before each effect, the runtime waits only as much as the checkpoint demands: completion if the effect consumes the task’s value, else its watermark — past its last trap-capable point — so “the task trapped” is always observed before “the print ran.”
  • When several independent steps could trap, the reported trap is the earliest in source order: the interpreter walk, sequential emission, and the parallel runtime’s minimum-index reporting all derive from the same topo_order key, so they cannot disagree. Output written before the trap is preserved.
  • The interpreter (mapal-interp: fueled graph evaluator + SCC loop driver) is the reference for all of this. On the default face compiled values are checked against it within the stated bound, in whatever order the compiler chose. In the development modes (--exact, --order=sequential|fixed) differential tests require compiled stdout/traps to match it byte-for-byte at -O0 and -O2, at any MAPAL_PAR, and under any CPU/GPU placement — for the examples and for programs from the random generator (ADR-0049 D3).
  • Device traps join the same order: a trap recorded by a device cell is raised at the next host checkpoint (a print, the clock, a host trap, the exit or a device-to-host copy), through mapal_rt_checkpoint_hook.

What is deterministic, and what is deliberately not. The compiler is deterministic: arena-ordered storage, source-ordered topo and rank-ordered tasks mean the same source produces the same emitted text, and traps are reported in source order. The values of floating-point combines are not promised bit for bit on the default face: parallel sums, atomics and stream-K walks may differ in the last bits between runs, always within the bound (ADR-0049). Bit-reproducible runs are a development mode, used to test and debug.

        position * inverse_frequencies[pair] -> angle;
        angle -> cos -> cosine;
        angle -> sin -> sine;
        (within_head < rotation_pairs) -> {
            -true-> x[cell] * cosine - x[cell + rotation_pairs] * sine;
            -false-> x[cell] * cosine + x[cell - rotation_pairs] * sine;
        }
    } -> ret;
}

// Building blocks. Activations are `tokens` vectors stored one after another.

fn embed<tokens>(embedding: Matrix<vocabulary_size, hidden_size>, ids: [i32; tokens]) -> [f32; tokens * hidden_size] {
    tokens * hidden_size -> iota -> map {
        cell ->
        ids[cell / hidden_size] * hidden_size + cell % hidden_size -> row_cell;
        embedding[row_cell] -> widen_f32
    } -> ret;
}

// RMSNorm of each vector: x / sqrt(mean(x^2) + epsilon), times a learned gain per feature.
fn rms_norm<tokens>(x: [f32; tokens * hidden_size], gain: [bf16; hidden_size]) -> [f32; tokens * hidden_size] {
    hidden_size -> iota -> features;
    hidden_size -> widen_f32 -> width;
    tokens -> iota -> map {
        t -> (0.0, features) -> fold {
            sum, i -> sum + x[t * hidden_size + i] * x[t * hidden_size + i]
        }
    } -> sum_of_squares;
    tokens * hidden_size -> iota -> map {
        cell ->
        sum_of_squares[cell / hidden_size] / width + rms_epsilon -> sqrt -> root;
        gain[cell % hidden_size] -> widen_f32 -> g;
        x[cell] * (1.0 / root) * g
    } -> ret;
}

// A linear layer without bias: out[t][row] = sum over columns of weight[row][column] * x[t][column].
fn project<tokens, rows, columns>(weight: Matrix<rows, columns>, x: [f32; tokens * columns]) -> [f32; tokens * rows] {
    columns -> iota -> along;
    tokens * rows -> iota -> map {
        cell ->
        cell / rows -> t;
        cell % rows -> row;
        (0.0, along) -> fold {
            sum, column ->
            weight[row * columns + column] -> widen_f32 -> w;
            sum + w * x[t * columns + column]
        }
    } -> ret;
}

fn add<n>(a: [f32; n], b: [f32; n]) -> [f32; n] {
    n -> iota -> map {
        i -> a[i] + b[i]
    } -> ret;
}

fn larger(a: f32, b: f32) -> f32 {
    (a > b) -> {
        -true-> a;
        -false-> b;
    } -> ret;
}

// SiLU, the gate activation of SwiGLU: x * sigmoid(x).
fn silu(x: f32) -> f32 {
    -x -> exp -> decay;
    x / (1.0 + decay) -> ret;
}

// ---------------------------------------------------------------------------------------------------------
// Attention.

// The cache with the chunk's rows (keys or values, one row per token) written at positions
// first_position, first_position + 1, ... of layer `layer`.
fn write_rows<tokens>(cache: [f32; cache_size], rows: [f32; tokens * key_value_size], layer: i32, first_position: i32) -> [f32; cache_size] {
    cache_size -> iota -> map {
        cell ->
        cell / key_value_size - layer * context_length - first_position -> t;
        (t >= 0 && t < tokens) -> {
            -true-> rows[t * key_value_size + cell % key_value_size];
            -false-> cache[cell];
        }
    } -> ret;
}

// Causal grouped-query attention over layer `layer`'s cached keys and values: each token's query head h reads
// key/value head h / 4 of every cached position up to its own, scores are scaled by 1 / sqrt(head_size),
// softmax over each head's scores, and the result is the weighted sum of the cached values.
fn attend<tokens>(
    query: [f32; tokens * query_size],
    positions: [i32; tokens],
    cache: KeyValueCache,
    layer: i32,
) -> [f32; tokens * query_size] {
    head_size -> iota -> dimensions;
    context_length -> iota -> past_positions;
    head_size -> widen_f32 -> sqrt -> scale_root;
    tokens * query_heads * context_length -> iota -> map {
        cell ->
        cell / context_length -> token_head;
        cell % context_length -> past;
        token_head / query_heads -> t;
        token_head % query_heads / heads_per_key_value_head -> key_value_head;
        (past <= positions[t]) -> {
            -true-> {
                (layer * context_length + past) * key_value_heads + key_value_head -> key_row;
                (0.0, dimensions) -> fold {
                    sum, d -> sum + query[token_head * head_size + d] * cache.keys[key_row * head_size + d]
                } -> dot;
                dot / scale_root
            }
            -false-> -1000000000.0;
        }
    } -> scores;
    tokens * query_heads -> iota -> token_heads;
    token_heads -> map {
        token_head -> (-1000000000.0, past_positions) -> fold {
            best, past -> (best, scores[token_head * context_length + past]) -> larger
        }
    } -> row_maximum;
    tokens * query_heads * context_length -> iota -> map {
        cell -> scores[cell] - row_maximum[cell / context_length] -> exp
    } -> exponentials;
    token_heads -> map {
        token_head -> (0.0, past_positions) -> fold {
            sum, past -> sum + exponentials[token_head * context_length + past]
        }
    } -> row_total;
    tokens * query_size -> iota -> map {
        cell ->
        cell / head_size -> token_head;
        cell % head_size -> d;
        token_head % query_heads / heads_per_key_value_head -> key_value_head;
        (0.0, past_positions) -> fold {
            sum, past ->
            (layer * context_length + past) * key_value_heads + key_value_head -> value_row;
            sum + exponentials[token_head * context_length + past] * cache.values[value_row * head_size + d]
        } -> weighted;
        weighted / row_total[token_head]
    } -> ret;
}

// The decoder layer and the whole model.

// SwiGLU feed-forward: down(silu(gate(x)) * up(x)).
fn feed_forward<tokens>(x: [f32; tokens * hidden_size], weights: DecoderLayerWeights) -> [f32; tokens * hidden_size] {
    (weights.gate, x) -> project -> gate: [f32; tokens * feed_forward_size];
    (weights.up, x) -> project -> up: [f32; tokens * feed_forward_size];
    tokens * feed_forward_size -> iota -> map {
        i ->
        gate[i] -> silu -> activated;
        activated * up[i]
    } -> mixed;
    (weights.down, mixed) -> project -> ret;
}

// One decoder layer over the chunk: attention with a residual connection, then the feed-forward block with
// a residual connection. The chunk's keys and values enter the cache before its queries attend.
fn decoder_layer<tokens>(
    hidden: [f32; tokens * hidden_size],
    weights: DecoderLayerWeights,
    layer: i32,
    cache: KeyValueCache,
    positions: [i32; tokens],
) -> ([f32; tokens * hidden_size], KeyValueCache) {
    (hidden, weights.attention_norm) -> rms_norm -> normed;
    (weights.query, normed) -> project -> query: [f32; tokens * query_size];
    (weights.key, normed) -> project -> key: [f32; tokens * key_value_size];
    (weights.value, normed) -> project -> value: [f32; tokens * key_value_size];
    (query, positions) -> rotate -> rotated_query;
    (key, positions) -> rotate -> rotated_key;
    (cache.keys, rotated_key, layer, positions[0]) -> write_rows -> keys;
    (cache.values, value, layer, positions[0]) -> write_rows -> values;
    KeyValueCache {
        keys: keys,
        values: values,
    } -> updated_cache;
    (rotated_query, positions, updated_cache, layer) -> attend -> attended;
    (weights.output, attended) -> project -> attention_output: [f32; tokens * hidden_size];
    (hidden, attention_output) -> add -> after_attention;
    (after_attention, weights.feed_forward_norm) -> rms_norm -> normed_again;
    (normed_again, weights) -> feed_forward -> feed_forward_output;
    (after_attention, feed_forward_output) -> add -> ret.0;
    updated_cache -> ret.1;
}

// Run a chunk of tokens, the first at `first_position`, through every layer; return the logits after the
// chunk's last token and the cache holding the chunk's keys and values.
fn forward<tokens>(ids: [i32; tokens], first_position: i32, model: Model, cache: KeyValueCache) -> ([f32; vocabulary_size], KeyValueCache) {
    tokens -> iota -> map {
        t -> first_position + t
    } -> positions;
    (model.embedding, ids) -> embed -> embedded;
    mut hidden: [f32; tokens * hidden_size] <- embedded;
    mut updated: KeyValueCache <- cache;
    mut layer: i32 <- 0;
    loop {
        (layer < layer_count) -> {
            -true-> {
                (hidden, model.layers[layer], layer, updated, positions) -> decoder_layer -> result;
                result.0 -> hidden;
                result.1 -> updated;
                layer + 1 -> layer;
                -> loop;
            }
            -false-> {
                hidden_size -> iota -> map {
                    i -> hidden[(tokens - 1) * hidden_size + i]
                } -> last;
                (last, model.final_norm) -> rms_norm -> normed;
                (model.embedding, normed) -> project -> logits: [f32; vocabulary_size];
                (logits, updated) -> ret;
            }
        }
    }
}

// Greedy decoding: the token with the largest logit (the first one on a tie).
fn most_likely_token(logits: [f32; vocabulary_size]) -> i32 {
    vocabulary_size -> iota -> tokens;
    ((logits[0], 0), tokens) -> fold {
        best, token -> (logits[token] > best.0) -> {
            -true-> (logits[token], token);
            -false-> best;
        }
    } -> winner;
    winner.1 -> ret;
}

fn main() {
    "model.bin" -> read -> model: Model;
    (0.0, cache_size) -> fill -> nothing_cached;
    KeyValueCache {
        keys: nothing_cached,
        values: nothing_cached,
    } -> empty_cache;

    // The prompt arrives (the clock starts), and all of it at once, from position 0, gives the first token.
    () -> time -> submitted;
    "prompt.bin" -> read -> prompt_file: [i32; prompt_file_length];
    prompt_length -> iota -> map {
        t -> prompt_file[t]
    } -> prompt;
    (prompt, 0, model, empty_cache) -> forward -> prefilled;
    prefilled.0 -> most_likely_token -> first_token;
    () -> time -> first_token_time;
    first_token -> print;
    " " -> print;
    prefilled.0[first_token] -> print;
    " " -> print;
    first_token_time - submitted -> println;

    // Each later token: feed the previous one at the next position.
    mut token: i32 <- first_token;
    mut cache: KeyValueCache <- prefilled.1;
    mut position: i32 <- prompt_length;
    loop {
        (position < prompt_length + generated_tokens - 1) -> {
            -true-> {
                [token] -> ids;
                (ids, position, model, cache) -> forward -> stepped;
                stepped.0 -> most_likely_token -> token;
                stepped.1 -> cache;
                () -> time -> now;
                token -> print;
                " " -> print;
                stepped.0[token] -> print;
                " " -> print;
                now - submitted -> println;
                position + 1 -> position;
                -> loop;
            }
            -false-> position -> last_position;
        }
    }
}

Source (§2)Top-level sizes from the checkpoint’s config (2048 -> hidden_size;); type Matrix<rows, columns> { _: [bf16; rows * columns] }; size-generic rms_norm<tokens>, project<tokens, rows, columns>, attend<tokens>; exp, sqrt, sin/cos for SiLU, RMSNorm and the rotary embedding; "model.bin" -> read -> model: Model;; a loop carrying the token, the key/value cache and the position.
Lower (§4)Top-level scalars computed by the interpreter and used as sizes; one fixed-size instance per size tuple — forward once for the prompt length and once for one token; read threads the IO token.
Facts (§6)static_plan: values that read no input (the rotary frequencies, for one) are embedded or computed at run time by its bytes-against-work rule. tile_plan/tensor_form: every projection is a tile site over bf16 storage (tile_plan_narrow). stream_plan: the prompt’s attention streams over key windows with a causal mask read through a positions array. unchanged_plan, access_plan, residence_plan: weights the same on every call; the cache written in place.
Placement (§8, today by rules)The decode step stays on the device (cand-made); the weights upload once (CSE value scope); the prompt writes its cache rows on the device and the loop takes the buffers (once-range, carry-take); projections on tensor cores in both classes (in the f32 class as a split form — two bf16 parts of each f32 activation against the bf16 weight, ADR-0044; 16-bit mma.sync, wgmma on the H100), the prompt’s attention as one streamed kernel.
NumericsTwo classes, compared type to type: the program as written (f32 activations, bf16 weights widened exactly in registers) and the bf16 class (fold: bf16 | f32, a bf16 key/value cache). Every value gate checks the bound; in the bf16 class the tensor tile adds partial sums in arrival order, so greedy tokens can vary from run to run — within the bound, as ADR-0049 allows.
